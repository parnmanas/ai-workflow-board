# Ontology Graph — Design Decisions (v1)

Date: 2026-08-22 (v1.1 — revised after a three-lens adversarial design review). This is a **decision document**, not a survey. It commits AWB's per-workspace Ontology Graph feature to one answer on each of six axes, states why in terms of the evidence already gathered, states what was explicitly rejected and why, and pins every decision to a real `file:line` in this repo so a child-ticket author has a starting point, not a research question.

**Revision note.** Three adversarial reviewers (scale, integrity, adoption lenses) stress-tested v1.0 of this document and returned 21 findings. Every one of them is incorporated below — either by changing the decision, adding a concrete mitigation, or explicitly rejecting the finding with a stated reason. `REVIEW-NOTES.md` in this directory is the verbatim record of all 21 findings plus a 1:1 resolution map; this file is the design *as revised*, not a diff. Where a fix required correcting a factual claim (e.g. FTS5's actual availability in `sql.js`), that correction is made here and flagged as such rather than silently absorbed.

**Inputs.** Five deep-research documents already reached strong, evidence-backed conclusions on axes 1–5 (`research-extraction.md`, `research-ontology.md`, `research-storage.md`, `research-incremental.md`, `research-visualization.md`); this document's job on those five axes is to carry those conclusions forward faithfully and make them concrete, not to re-litigate them. `research-agent-consumption.md` is newly researched and axis 6 (MCP tool surface) is decided here for the first time, treating its §5 "Decisive recommendation" as the v1 working design (see axis 6 "Why" for why this is now explicitly framed as *provisional*, not permanently binding — a direct response to the adoption-lens review). `research-prior-art.md` is not an axis — it is the adoption-risk stress test that shapes the scope fence in §10. `scout-client.md` and `scout-server.md` ground every axis in the current worktree's actual source, not an imagined one.

**Scope.** This ticket is research/design-only. No production code ships from it. Every decision below is sized to be implementable by a focused child ticket; §10 is the explicit fence around what those child tickets should *not* attempt in v1.

**Bottom line up front.** Build: (1) a mandatory tree-sitter-WASM extraction tier plus a confidence-scored cross-file resolver — with an explicit, bounded-complexity fuzzy-match tier, transitive barrel/re-export resolution, a reflection/decorator-aware discount category, and a polymorphic-dispatch confidence cap — and SCIP, LSP, and LLM enrichment as strictly optional, budgeted, non-blocking tiers layered on top, with LLM-derived confidence values computed by a shared ingest helper (never self-reported by the model) exactly as strictly as the existing layer write-scope rule; (2) a two-namespace labelled-property-graph schema — a SEON/SCIP-derived structural side and a SKOS-derived semantic side, joined by exactly one bridge-edge class, with a mandatory `layer` discriminator, a pinned `resolution` enum, and write-scope enforcement — stored relationally, never as a live RDF/OWL store; (3) SQLite (`sql.js`, dev, **in its own independently-flushed DataSource so ontology-table growth cannot inflate the primary OLTP file's flush cost**) / PostgreSQL (prod, single DataSource, unaffected) as the *only* storage engine, queried through bounded-depth recursive CTEs and application-orchestrated BFS — every traversal confidence-floored by default — never Kuzu, never an unbounded recursive CTE, never a second graph database; (4) a four-mechanism incremental pipeline — stable `symbol_id` identity, a signature/body-split early-cutoff hash, a materialized reverse-edge index, and durability tiers, **plus an unconditional rename/move re-resolution branch** — that keeps a single-file body-only edit sub-second (hot-symbol signature changes at realistic multi-thousand fan-in are an explicitly separate, unmeasured case, not covered by that claim) and treats SCIP/LSP/LLM enrichment as explicitly lazy and batch, never live, with staleness convergence surfaced honestly rather than assumed; (5) sigma.js as the default aggregated-view renderer **gated on a pre-ship measurement of actual Leiden community counts at scale**, with cosmos.gl as a deliberate opt-in raw-mode escape hatch, Leiden (never Louvain) for community detection, a position-persistence contract, **an explicit layer/confidence visual encoding**, and **a mandatory freshness badge**; (6) a **graph-lifecycle-aware**, six-to-seven-tool MCP surface built *on top of*, never duplicating, the three fixed bounded-traversal tools already named in `research-storage.md` — a new `graph_status` tool resolves-or-provisions a `graph_id` from `(workspace_id, resource_id, folder_path)` so no tool ever presupposes a graph that doesn't exist yet; `graph_find_symbol`, `graph_module_summary`, and `graph_status` ship first in the same PR with a default `confidence_min=0.75` applied uniformly across **all six** traversal/lookup tools (not just the two newest); `graph_search_symbols` ships second gated behind the embedding-provider check; `graph_hotspots` is deferred to backlog; and MCP tool-call recurrence (not first-opens) is logged from wave 1 so the human-facing rendering engine (child ticket #8) ships only once that data shows real repeat use.

## 1. Scale, restated up front

These are the numbers every other decision in this document is sized against. All measured directly on the AWB host (`research-extraction.md` §1): **771 TS/TSX/JS files, 197.5 kLOC, 9.24 MB**, single-threaded.

- **web-tree-sitter (WASM) 0.25.10:** total wall 2.42 s → **81,727 lines/s** end-to-end (parse + query + extract); parse-only 1.56 s → 126,654 lines/s; 106,654 captures; 8 files (1.0%) had parse errors; RSS 234 MB.
- **node-tree-sitter (native N-API):** parse-only 1.15 s → 171,877 lines/s (native is ~1.36× faster than WASM on parse — the 36% is worth paying for WASM's zero-toolchain, 371-grammar distribution instead).
- **Measured density (the number storage/rendering must be sized against):** **27.6 definitions/kLOC**, **243.6 references/kLOC** (5,459 defs / 48,113 refs over 197.5 kLOC). Definition breakdown: method 2,200, function 1,634, interface 937, class 443, type 245. Reference breakdown: call 43,346, import 4,767.

**Extrapolation table** (`research-extraction.md` §1), the sizing basis for storage (axis 3), incremental refresh (axis 4), and rendering (axis 5):

| Repo size | Parse+extract, 1 thread | 8 workers | Def nodes | Ref edges (raw) |
|---|---|---|---|---|
| 200 kLOC | 2.4 s | ~0.4 s | 5.5k | 48k |
| 1 MLOC | ~12 s | ~1.8 s | ~28k | ~244k |
| 10 MLOC | ~2 min | ~18 s | ~280k | ~2.4M |
| 100 MLOC | ~20 min | ~2.6 min | ~2.8M | ~24M |

Independent corroboration at comparable and larger scale (`research-extraction.md` §1, `research-ontology.md` §4.4): Codebase-Memory indexes **Django (49,398 nodes / 196,022 edges) in ~6 s** and the **Linux kernel (≈30 MLOC) into 2.1M nodes / 4.9M edges in ~3 minutes**, with incremental re-index at **~1.2 s**; a production RFC quotes tree-sitter at **≈100k lines/second** with single-file update latency of **50–200 ms**, versus **60–120 s** for a full SCIP reindex on the same repo. **Read this as: the syntactic pass (Tier 1) is essentially free at any size AWB will see.** That claim is scoped deliberately narrowly — it covers Tier 1 (raw def/ref extraction) only. **Tier 1.5 (the mandatory cross-file confidence-scored resolver, without which the output is an unconnected forest of per-file symbol lists, not a graph — axis 1 line ~66) has zero measured wall-clock number anywhere in this corpus**, before or after this revision; `research-extraction.md`'s own text calls it "cheap" by adjective only. This is a real, open benchmarking gap, not a rounding error, since axis 1 itself states Tier 1.5 is required for queryability. **Action, not yet a number:** before citing "essentially free at any size" as covering the *whole* mandatory pipeline (Tier 1 + Tier 1.5), a child ticket must benchmark Tier 1.5 end-to-end on AWB's own 197.5 kLOC corpus — the same one Tier 1 was measured against — and report a real number. Until that exists, treat "essentially free" as a Tier-1-only claim. **The cost centers this design must actually manage are storage/query shape (axis 3), the resolver + semantic-layer staleness bookkeeping (axis 4), any LLM pass (axes 1 and 4), and — newly identified in this revision — the write-side cost of persisting the resulting graph on AWB's dev backend (axis 3) — never parsing.**

## 2. Data flow, in words

1. **Extraction (Tier 1, mandatory).** A tree-sitter WASM worker pool reads a repo folder through AWB's existing git cache (`git-repo-cache.ts`'s `listTree`/`getFileContent`, see axis 1 §"Integration points"), parses each changed file, and emits a per-file fact bundle: `defs[]`, `refs[]` (unresolved — name + qualifier + call-shape), `imports[]`, `exports[]`, `heritage[]`, `docstrings[]`, plus `file_hash` (XXH3) and `extractor_version`. Nothing here touches another file.
2. **Cross-file resolution (Tier 1.5, mandatory).** A confidence-scored resolver turns each file's `refs[]` into `CALLS`/`REFERENCES` edges against the workspace-wide symbol table, using a cascade (import-map → same-module → import-suffix → unique-name → suffix → fuzzy) that assigns `confidence` + `resolver` provenance to every edge it produces — never a bare, unqualified edge. The import-map tier follows `export ... from` re-export/barrel chains transitively to their defining file rather than stopping at the first hop (axis 1). The fuzzy tier is a bounded-complexity, dependency-free in-process lookup, not pairwise comparison (axis 1/3). A resolved `CALLS` target that itself has `OVERRIDES`/`IMPLEMENTS` siblings is capped at `resolution='dynamic'` regardless of which tier matched — including SCIP-resolved edges (axis 2).
3. **Optional semantic upgrade (Tier 2 / 2b / 3).** If a repo opts in: SCIP ingest (out-of-process, in the agent's already-dependency-installed worktree) upgrades matching Tier-1.5 edges to `confidence=1.0` as an immutable layer keyed by `(repo, commit, indexer, indexer_version)` — subject to the same polymorphic-dispatch cap above; LSP answers one-off precise queries on demand; a budgeted, bottom-up LLM pass writes `semantic`-layer `Concept`/`Term` nodes and `REALIZES`/`MENTIONS` edges onto aggregate nodes only (folder/module/class, never function), with `confidence` **computed by a shared ingest helper from k-sample agreement or evidence-chunk count — never returned by the LLM call itself** (axis 1). An optional, v1-scoped-but-still-opt-in `@ast-grep/napi` ruleset covers framework-reflection-driven dispatch (NestJS guards/interceptors/pipes/`@Cron()`/`@EventPattern()`) as a `DECORATES` edge, confidence-discounted below name-resolved tiers (axis 1/2). None of this sits on the write path.
4. **Storage (write path).** All of the above lands in the relational `OntologyNode`/`OntologyEdge` tables — on the sql.js (dev) backend, in a **second, independently-flushed DataSource/file dedicated to ontology data**, never sharing the primary OLTP `data.db`'s dirty flag or flush timer; on Postgres (prod), alongside everything else in the single existing DataSource, unaffected (axis 3). Tagged with `layer`, `graph_id`, and stable `symbol_id`. Leiden clustering runs over the aggregated structural edge set to populate `Community`/`MEMBER_OF` derived-layer rows, at every `level` the schema already supports (axis 5).
5. **Incremental refresh (on file save, debounced, or on `git diff` at commit/branch-switch granularity).** Phase A re-parses only the changed file and diffs its symbol table by `symbol_id`; if every changed symbol's `signature_hash` is unchanged (a body-only edit), refresh **stops here** — no other file is touched. **A rename/move detected via `-M` is a third, unconditional Phase-B trigger, independent of `signature_hash`**: the moved file's own outgoing `refs[]` are always re-run through Tier-1.5, because two of its cascade tiers are path-relative and a move can silently shift their resolution targets even though nothing about the file's own declared shape changed (axis 4). Phase B, for symbols whose signature actually changed/was added/removed (or for a rename, per above), walks a materialized `reverse_edge_index` (file-level first, symbol-level second, skipping `stable`/`frozen`-durability partitions entirely) and re-runs the Tier-1.5 resolver only for the returned files. Phase C flips any `semantic`/`derived` edge whose cited `evidence_ref` content hash no longer matches to `status='stale'` — no LLM call, ever, on this path. A background sweep later drains the stale queue in priority order (open folder → active-ticket folder → centrality) under a token budget, using the Anthropic Batch API and prompt caching — **this is a cost cap, not a convergence guarantee; §5's own power-law fan-in finding means a sufficiently large, sufficiently active repo can see the stale backlog grow rather than shrink, and this design responds with honest surfacing (below), not an unverified convergence claim** (axis 4).
6. **Query API (read path).** A small internal graph-query service — never exposed as free-form SQL — answers bounded-depth, cycle-guarded recursive CTEs for neighbor/blast-radius queries and application-orchestrated bidirectional level-BFS for call-path queries, all scoped by `graph_id` **and, by default, floored at `confidence >= 0.75`** on every edge traversed, not just on the two newest lookup tools (axis 3/6). A scheduled, read-only DuckDB `ATTACH` sidecar separately computes OLAP-shaped aggregates (degree distributions, top-fan-in symbols) into a small stats table, off the query path entirely.
7. **Graph lifecycle (new).** A `graph_status(workspace_id, resource_id, folder_path)` call resolves the `OntologyGraph` row for that triple, auto-provisioning one and kicking off Tier 1/1.5 extraction as an async background job on first reference — no tool anywhere requires a caller to already possess a `graph_id` it has no way to obtain (axis 6).
8. **MCP tools (agent consumption).** `graph_status`, `graph_find_symbol`, `graph_module_summary`, (later) `graph_search_symbols`, and the three fixed traversal tools (`graph_neighbors`, `graph_blast_radius`, `graph_call_path`) wrap the query API. Every response carries `path`/`start_line`/`end_line` (so the agent can verify by reading source), `{source, confidence, indexed_at, commit}` (so the agent knows how much to trust it), and `completeness` (so "no results" and "no results, known-incomplete coverage" are distinguishable), bounded to 20–50 rows by default. `graph_call_path` additionally returns a single labelled `path_confidence` (min-along-path, never multiplied) rollup. Tool-call frequency is logged from wave 1 (axis 6).
9. **UI rendering (human consumption).** The same query API and the same bounded-BFS "Expand" call feed a sigma.js aggregated Community/Module view by default (pending the pre-ship community-count measurement, axis 5), with camera-driven semantic zoom (`nodeReducer`/`camera.ratio`) walking down to declaration-level nodes, `edgeReducer`-driven layer/confidence visual encoding, a persistent freshness badge, and a deliberate opt-in switch to a GPU-simulated cosmos.gl raw view past sigma's practical ceiling.

## 3. Cross-cutting invariants

These recur in every axis below and are not re-derived per axis — they are load-bearing constraints the whole design depends on:

- **`layer` discriminator on every node and edge** (`structural | derived | semantic | curated`), with a service-layer write-scope rule: an LLM/semantic extraction run may only insert `Concept|Term|Policy|Actor|Capability` nodes and `REALIZES|MENTIONS|BROADER|NARROWER|RELATED|CLOSE_MATCH|GOVERNS|DESCRIBES` edges — it may never create, mutate, or delete a `structural`/`derived` row (`research-ontology.md` §8.2). **The same service-layer discipline now applies to the confidence *value* itself, not just the row type** (axis 1/2): an LLM extraction call's structured-output schema must never include a `confidence` field at all; a single shared ingest helper computes it from k-sample agreement or evidence-chunk count and is the only code path permitted to set `confidence_method='agreement'`. A schema column an implementer can freely populate is not a validated invariant — this closes that specific gap.
- **Stable, content/path-derived `symbol_id`** (SCIP-shaped, version-stripped) as the join key for every incremental mechanism, every position-persistence mechanism, and every curated-annotation reattachment (`research-ontology.md` §5.3, §7; `research-incremental.md` §1.3's CodeQL counter-id postmortem is the cautionary evidence for why this is non-negotiable).
- **Every edge that isn't `confidence=1.0` from an exact compiler-grade indexer carries `confidence` + `confidence_method` + provenance** (`source`, `resolver`/`model_id`, `indexed_at`, `commit`) — never a bare float, never an unqualified fact (`research-ontology.md` §6). **A resolved edge's `resolution` enum value is pinned in this document, not just cited from research** (`exact | name_match | dynamic | unresolved`), and any edge whose target has `OVERRIDES`/`IMPLEMENTS` siblings is capped at `resolution='dynamic'` regardless of which tier or indexer produced it — name-resolution confidence and runtime-dispatch confidence are two different axes and are never collapsed into one number (axis 2). **Any multi-edge path this design returns carries exactly one labelled, derived path-level confidence (e.g. `graph_call_path`'s `path_confidence`, min-along-path) — never a bare per-edge list an agent must roll up itself, and never a multiplied value** (`research-ontology.md` §6.5; axis 6).
- **Every graph-shaped query is bounded** — depth-capped, `LIMIT`-capped, never a single unbounded recursive CTE, never a full transitive-closure precompute (`research-storage.md` §2.3–2.5; this is why axis 6's MCP tools compose with axis 3's query engine instead of reimplementing traversal). **Every bounded traversal is also confidence-floored by default** (`confidence_min=0.75`, overridable) — bounded-but-untrusted is not a safe default for a tool an agent uses to decide what's safe to change (axis 3/6).
- **Every AWB-facing query is `graph_id`-scoped**, and `graph_id` scopes to `(workspace_id, resource_id, folder_path)` — a per-folder graph, not a platform-wide one (`research-ontology.md` §8.1; this is also the single biggest performance lever per `research-storage.md` §8 point 2). **No tool ever requires a `graph_id` the caller has no way to obtain** — `graph_status` resolves-or-provisions one from the same `(workspace_id, resource_id, folder_path)` triple (axis 6).
- **Aggregate, never raw.** Reference edges are stored/rendered/returned collapsed by target (module, symbol pair, or community), never as one row per call site — a 3–10× storage cut, a rendering necessity past sigma's ceiling, and a tool-output-size discipline all at once (`research-extraction.md` trap #5; `research-agent-consumption.md` §3.3).
- **Freshness is surfaced, never implied.** Every MCP response's `{indexed_at, commit}` and the UI's persistent freshness badge (axis 5) are the same honesty discipline applied to two different audiences — a graph that looks authoritative but is quietly stale is treated as worse than no graph at all (`research-prior-art.md` §6 pitfall #5), and this design does not claim the background sweep (axis 4) guarantees eventual freshness — it guarantees the *staleness is visible* when convergence isn't proven.

## Axis 1 — Extraction pipeline

### Decision

A **three-tier extraction pipeline** with exactly one mandatory tier: **Tier 1 (tree-sitter tags, in-process, WASM) plus Tier 1.5 (a confidence-scored cross-file resolver)** are always-on and sufficient on their own for the graph to be queryable. **Tier 2 (SCIP ingest) and Tier 2b (LSP-on-demand)** are optional, per-repo opt-in, run out-of-process in the agent's already-dependency-installed worktree, and never touch the write path. **Tier 3 (bounded, budgeted LLM enrichment)** is optional, applied only to aggregate nodes (folder/module/class — never function), cached by subtree content hash, and never required for queryability.

Concretely: `web-tree-sitter` (WASM) in a `worker_threads` pool (or a dedicated process), grammars from `kreuzberg-dev/tree-sitter-language-pack` (371 languages, ABI 14, MIT) with `tree-sitter-wasms`/`@vscode/tree-sitter-wasm` as a bundled fallback for the top ~20 languages; per-language extraction is a versioned `tags.scm`-style query file plus an optional `@ast-grep/napi` ruleset for framework-level concepts (routes, DI providers, entities); output is per-file fact bundles (`defs[]`, `refs[]`, `imports[]`, `exports[]`, `heritage[]`, `docstrings[]`, `file_hash`, `extractor_version`) — never global state. Tier 1.5 is a separate, whole-workspace pass using the Codebase-Memory confidence cascade (import-map 0.95 → same-module 0.90 → import-suffix 0.85 → unique-name 0.75 → suffix 0.55 → fuzzy ~0.35), storing `confidence` + `resolver` on every produced edge.

**Import-map tier resolves transitively through barrels/re-exports (review finding, integrity/minor).** The import-map tier (0.95) follows `export ... from` re-export chains to their ultimate defining file — not just the first hop — before falling through to lower tiers. This matters concretely for AWB's own reference codebase: `apps/server/src/entities/index.ts` barrel-exports every entity, and DESIGN.md's own integration points cite this pattern repeatedly as the worked example. Without transitive resolution, an entity import resolved through that barrel would register at "likely" (0.55–0.75) confidence rather than "asserted" (0.95+) on the single most common import shape in AWB's own codebase — understating confidence in the common case and risking a wrong pick if two barrels in a larger monorepo re-export same-named symbols. Bounded by the calling file's own import-graph depth (rarely more than 3–4 hops in practice), not by workspace size. Child ticket #3 (resolver) adds a repo-representative test fixture mirroring `entities/index.ts`.

**Fuzzy tier is a bounded-complexity, dependency-free structure, not pairwise comparison — and a factual correction to an earlier proposal (review finding, scale/minor).** No prior revision of this document stated a data structure or complexity bound for the fuzzy (~0.35) tier. Implemented naively as pairwise string-similarity between an unresolved reference and the workspace symbol table, it would be the one place in an otherwise carefully bounded design (extraction is linear per `research-extraction.md` §1; storage/query is depth-capped per `research-storage.md` §2.4) that becomes genuinely O(refs × defs) — at the design's own measured density, even a modest 5% fuzzy-fallback rate at 10 MLOC is ~120k references potentially compared against a ~280k-symbol table each. The fix is an **in-process JS-side bounded structure** — a BK-tree (or equivalent metric tree) over the workspace's symbol-name table, built once per extraction run and updated incrementally alongside Tier 1.5's other tiers, giving O(log n) approximate-match lookups per unresolved reference instead of O(n) pairwise comparison: ~120k lookups × O(log 280k) is on the order of a few million comparisons, not tens of billions. **A specific technical claim needs correcting here, not just adopting**: an earlier draft of this fix proposed SQLite FTS5 (a trigram-capable full-text index) on the grounds that it's "compiled into `sql.js`." It is not, by default — `sql.js`'s official distributed build enables FTS3 only; FTS5 requires a custom Emscripten rebuild with `-DSQLITE_ENABLE_FTS5` in `CFLAGS` (confirmed against the `sql.js` project's own build documentation; re-verify against the exact pinned `sql.js@1.12.0` artifact before implementation). That is the *same* "fork `sql.js` to get this feature" cost class axis 3 already rejected for `sqlite-vec` (`research-storage.md` §6.1) — for consistency, this design rejects it here too, in favor of the dependency-free JS-side BK-tree, which needs no SQLite extension of any kind, loadable or compiled-in, on either backend.

**Tier 3 confidence must be computed, never self-reported (review finding, integrity/major — shared with axis 2's write-scope invariant and axis 4's sweep).** `research-ontology.md` §6 point 3's own cited evidence is that "different LLMs... produce knowledge graphs that scarcely overlap" and that self-reported confidence is therefore not a measurement — but prior to this revision, nothing in axis 1 or axis 4's Decision text actually enforced that, only cited it as background for the axis-2 schema choice. A child ticket implementing Tier 3 could satisfy every schema constraint this document specified while simply asking the LLM for a 0–1 confidence number and writing it through as `confidence_method='agreement'` — the exact practice the cited evidence disqualifies — and nothing would catch it, because the enum value was asserted, not verified. Fixed here as a concrete algorithm, not adjective-only: the LLM extraction call's structured-output response schema **must never include a `confidence` field**; a single shared ingest helper (living in the same service layer that owns the axis-2 layer write-scope check) computes `confidence` from k-sample self-consistency agreement or independent-evidence-chunk count and is the *only* code path permitted to write `confidence_method`.

**Tier-3 first-pass cost, recomputed for the actually-adopted (aggregate-only) approach, not the rejected (per-function) one (review finding, scale/major).** Every cost figure in the pre-review corpus ($10–30/MLOC, ~28k calls/MLOC) was computed for the explicitly rejected per-function approach and never recomputed for what axis 1 actually adopted (aggregate nodes only). Doing that recomputation honestly, with the numbers this corpus already publishes: `research-storage.md` §6.3 estimates **~100k–150k aggregate nodes** (class + interface + file + folder) at the 10 MLOC / ~280k-def scale, versus ~280k per-function nodes in the rejected estimate — a ~2× cut, not the order-of-magnitude the "biggest cost-blowup risk, fixed" framing implied. Per-call cost moves the other direction: HCGS-style bottom-up aggregate summarization (`research-extraction.md` §2.13) sends a full file/folder's content plus its already-computed child summaries per call — call it an order-of-magnitude **1,500–4,000 input tokens/call** for a typical file-sized aggregate node (this range is a reasoned estimate from this corpus's own file-size numbers, not a benchmark — no document measures actual token counts for this call shape), 2.5×–6.5× the rejected estimate's flat 600-token/call baseline. Multiplying: ~100k–150k nodes × ~1,500–4,000 tokens ≈ **150M–600M input tokens** for an uncached first pass (a newly onboarded large repo has no warm prompt cache to lean on — `research-incremental.md` §5.1's own ~5-minute default TTL caveat means a slowly-draining initial sweep may never realize the claimed cache discount). At the already-cited $0.50/M input tokens, that is roughly **$75–$300** for one full first-pass sweep of a 10 MLOC repo — plausibly the *same order of magnitude* as the rejected per-function approach's own $100–300 (10 MLOC × $10–30/MLOC) ballpark, not a clean order-of-magnitude win. **This is a genuine, honest recomputation using this corpus's own numbers, not a new empirical measurement** — a child ticket must still benchmark a real Tier-3 first-pass run before the opt-in budget default is sized, and that default must be sized around this real number, not the rejected approach's number.

### Why

`research-extraction.md`'s own bottom-line-up-front states this directly: "build a tree-sitter tags pass as the mandatory always-on tier... add an optional SCIP tier... and use LLM only for a bounded enrichment layer." §5.1 ("Recommended stack for AWB — Extraction") specifies the worker-pool/WASM/grammar-bundle shape verbatim. §4 ("Hybrid pipelines") establishes that *every* production system in this space converges on the same tiered-fallback ladder (Sourcegraph's precise-vs-search-based layering, Meta Glean's semantic-as-ingest pattern, stack-graphs' file-isolated-skeleton-then-resolve pattern), differing only in where the line is drawn — AWB draws it at "syntactic is mandatory, everything semantic is optional and never blocking," which §6 trap #3 states as "the semantic tier is a freshness trap, not a quality upgrade" (SCIP indexers are whole-project: 60–120 s to reflect a one-line change on a 10k-file repo). `research-prior-art.md`'s independent stress test reinforces this from the opposite direction: Aider's repo-map gets real, shipped value from Tier 1 alone — tree-sitter + PageRank + a token budget, zero persistence, zero LLM, rebuilt from scratch every call (§4.1–4.3) — which is direct evidence Tier 1 is independently valuable and every tier stacked on top of it must earn its keep against that free baseline (pitfall #6).

### Rejected

- **GitHub `stack-graphs`** — archived 2025-09-09, last release Dec 2024, Rust-only with no maintained Node binding (`research-extraction.md` §0, §2.5). The *design* (file-isolated subgraphs, deferred cross-file resolution) is stolen for Tier 1/1.5's shape; the dependency is not taken.
- **Google Kythe** — requires an *instrumented build* to capture compilation units, which is a non-starter for arbitrary user repos AWB doesn't control the build of; team laid off April 2024, last stable release v0.0.53 (2021) (§2.7).
- **Meta Glean** — not embeddable in Node (Haskell + Hack + Thrift + RocksDB); the *schema philosophy* (facts + derived predicates + immutable layers) is stolen for axis 2/4, the software is not (§2.6).
- **Joern / Code Property Graphs** — full AST∪CFG∪PDG dataflow is heavy, superlinear, JVM-only, RAM-bound; right answer for a hypothetical future taint-analysis plugin, wrong answer for a general multi-language ontology graph built on every push (§2.8; kept explicitly out of v1, §10).
- **Semgrep / OpenGrep** — OSS engine is intraprocedural-only; cross-file analysis is a proprietary binary (Semgrep) or a separate community fork (OpenGrep); wrong tool for graph *construction* regardless (rule-per-pattern, no whole-program symbol table) (§2.10).
- **universal-ctags** — GPL-2.0 (a real linking/bundling problem), and yields definitions only, no references, no call edges; tree-sitter dominates it at the same measured speed (1.618 s ctags vs 1.645 s tree-sitter over ~2,700 Go files) while also providing structure and references (§2.11).
- **srcML** — GPL-3.0, only 5 languages, ~4.5× source-size XML output (§2.12).
- **LSIF** — legacy; Sourcegraph's own LSIF indexers are archived; accepted only as an *import* format if a repo already has one, never emitted (§2.4).
- **Unbudgeted, per-function LLM extraction** — at the measured 27.6 defs/kLOC, 1 MLOC is ~28k LLM calls, against a 12-second structural pass; this is "the single biggest cost-blowup risk in the feature" (§2.13) — hence Tier 3 is restricted to aggregate nodes, budgeted, cached, and opt-in, never a default-on per-symbol pass. (**Still rejected after this revision's recomputation above** — the adopted approach's real first-pass cost turned out closer to the rejected approach's than initially implied, which is exactly why the opt-in/budgeted/never-required-for-queryability framing carries the actual weight here, not the "order of magnitude cheaper" claim.)
- **SQLite FTS5 for the fuzzy-match tier** — factually rejected in this revision: not compiled into `sql.js`'s default distribution (only FTS3 is), so adopting it would mean forking `sql.js`, the same cost class already rejected for `sqlite-vec`; a dependency-free JS-side BK-tree is adopted instead (see Decision above).
- **Model-self-reported `confidence` for Tier 3 output** — explicitly rejected in this revision regardless of what `confidence_method` value it claims; the LLM response schema must not carry a `confidence` field at all (see Decision above).

### Integration points

- **`apps/server/src/modules/mcp/shared/git-repo-cache.ts`** is the real clone/fetch engine an extraction worker must reuse, not reimplement: `ensureRepoCache()` (`:222-269`) clones/fetches a bare, blobless cache per Resource; `listTree(repoPath, ref, treePath)` (`:551-570`) and `getFileContent(repoPath, ref, filePath)` (`:606-645`) are already folder-scoped and path-safety-checked via `normalizeRepoPath()` (`:363-370`) (`scout-server.md` §3b). **There is no MCP tool wrapping these yet** — if extraction is agent-driven rather than a server-side job, a new tool is required (`scout-server.md` §3b, §7 "Extraction worker ticket"). **This is also, independently, the free baseline the whole feature is measured against** — see axis 6 "Why" for why that comparison matters and was previously left unstated.
- **`apps/server/src/entities/Ticket.ts:119-126`** (`base_repo_resource_id` + `base_branch`, plain `varchar`, no DB FK) is the existing convention for "resource + branch" scoping a new Ontology entity's `resource_id`/`folder_path` columns should follow — plain columns, validated in application code, not a DB-level FK (`scout-server.md` §1).
- **A minimal NestJS-aware `@ast-grep/napi` ruleset is now committed as explicit v1 child-ticket scope, not left unspecified-optional (review finding, integrity/major).** AWB's own dogfood target (its own NestJS server) depends on decorator/reflection-driven dispatch tree-sitter's tags query cannot see at all: guards/interceptors/pipes/DI-provider resolution are invoked by the framework via `reflect-metadata`, not by any literal call site. A `graph_blast_radius` query on, say, `AuthGuard.canActivate` would otherwise return a near-empty result indistinguishable from "confirmed nothing calls this." Fix: a named minimal ruleset — guards, interceptors, pipes, `@Cron()`, `@EventPattern()` — producing `DECORATES` edges (axis 2) at a confidence tier explicitly *below* Tier 1.5's name-resolved floor (`confidence≈0.6, method='constant', resolution='dynamic'`, since it is framework-pattern-matched, not a resolved reference) — meaning axis 6's default `confidence_min=0.75` filter hides these unless an agent explicitly lowers the floor, which is itself the honest behavior for an inherently less-certain edge class. It remains optional/non-blocking (queryability never depends on it), but its *scope* is now pinned rather than an unspecified future possibility, per `research-prior-art.md` §6 pitfall #4's budget-additively-against-real-demand discipline.

## Axis 2 — Schema

### Decision

A **labelled-property-hybrid graph**: nodes and edges stored in two relational tables (mirroring `RelationTuple.ts`'s subject/relation/object shape), with every type given an IRI-shaped canonical name for standards interop, but **no live RDF/OWL triple store**. The graph splits into **two disjoint node namespaces joined by exactly one class of bridge edge**:

- **Hard side (`layer='structural'`)**: a SEON-`code.owl`-derived, declaration-granularity structure — `Repository, Directory, File, Module, Type, Callable, Field, Endpoint, DataEntity, ExternalPackage, Doc` — identified by a stable, SCIP-shaped `symbol_id`, produced only by deterministic extractors, never by an LLM.
- **Derived side (`layer='derived'`)**: `Community`, `CommunityReport`, `Metric`, `Clone`, `Hotspot` — deterministic algorithms (Leiden, co-change) over the structural graph.
- **Soft side (`layer='semantic'`/`'curated'`)**: a SKOS-shaped concept scheme — `ConceptScheme, Concept, Term, Actor, Policy` with a small closed `kind` enum — deliberately *not* OWL classes, so soft concepts can never entail anything about hard facts.
- **Bridge**: `REALIZES` (code → Concept) and `MENTIONS` (Doc/File → Concept), each carrying mandatory `evidence_ref` (content-hashed), `confidence` + `confidence_method`, `support`, `model_id`, `prompt_version`, `rank`. This is the *only* place the two worlds touch.
- **AWB-specific bridge (the differentiator)**: `AFFECTS_CODE` (Ticket → code node, direct SEON `affectsCodeEntity` precedent) and `ABOUT` (Ticket → Concept) — schema'd in v1, population deferred (§10).

Every node carries: `id, graph_id, symbol_id (UNIQUE per graph), type, kind, layer, name, qualified_name, path, start_line, end_line, content_hash, status, confidence, confidence_method, first_seen_commit, last_seen_commit, valid_from_commit, valid_to_commit, extraction_run_id, embedding_id, degree, pagerank`. Structural edge kinds: `CONTAINS` · `DECLARES` · `IMPORTS` · `CALLS` (+`resolution`, `call_count`) · `REFERENCES` · `USES_TYPE` · `EXTENDS` · `IMPLEMENTS` · `OVERRIDES` · `INSTANTIATES` · `RETURNS_TYPE` · `THROWS` · `READS`/`WRITES` · `DEPENDS_ON` · `TESTS` · `EXPOSES` · `CALLS_HTTP` · `PERSISTS_TO` · `DOCUMENTS` · **`DECORATES`** (added in this revision — decorator/reflection-applied metadata, e.g. a NestJS `@UseGuards(AuthGuard)` on a route handler; produced only by the optional ast-grep ruleset, axis 1, never by tree-sitter tags alone). Every edge additionally carries `evidence_kind, evidence_ref, rank, completeness, resolution (structural only)`.

**`resolution` is now a pinned enum in this Decision text, not merely named (review finding, integrity/major).** `resolution ENUM('exact', 'name_match', 'dynamic', 'unresolved')` — a prior revision named the column but left its actual values sourced only from `research-ontology.md`'s Why section, which meant even the one field that could flag "this edge might be dynamic dispatch" was not itself a committed part of the binding decision.

**Name-resolution confidence and runtime-dispatch confidence are two different axes, and this design no longer collapses them into one number (review finding, integrity/major).** Tier 1.5's cascade grades confidence purely by which name-matching heuristic fired — "how sure am I this identifier names symbol X," not "how sure am I X is what executes at runtime." A call through an interface-typed or base-class-typed reference resolves to exactly one name-tier target and inherits that tier's confidence, even though a polymorphic call site has a distinct, unaddressed axis of uncertainty. It gets worse at Tier 2: SCIP resolves to the compiler-declared symbol — a genuinely exact *name* reference — but a prior revision blanket-stamped any SCIP edge `confidence=1.0`, collapsing "exact reference to a declaration" and "exact claim about what executes at runtime" into one number for exactly the call sites (polymorphic dispatch) no compiler-grade indexer can close without whole-program points-to analysis (explicitly out of scope, Joern rejected in axis 1). **Fix, decided here**: after Tier 1.5 and/or SCIP resolution produces a `CALLS` target, a join against that target's own `OVERRIDES`/`IMPLEMENTS` incoming edges runs as a mandatory post-processing step; if the target has any such siblings, the edge's `resolution` is capped at `'dynamic'` **regardless of which tier or indexer produced the name match**, including SCIP. `confidence` itself is left as computed by the name-resolution cascade (or `1.0` for SCIP) — `resolution` is the separate, honest signal that the *name* is certain but the *runtime target* is not.

Confidence uses `confidence_method ENUM('constant','agreement','support','calibrated','human')` and is surfaced in ordinal buckets (`asserted ≥0.9 / likely 0.6–0.9 / speculative <0.6`) — never a bare float; the mechanism that keeps `confidence_method='agreement'` honest (never model-self-reported) is specified in axis 1's Decision and enforced as a service-layer invariant, the same way the layer write-scope rule below is (not a schema column an implementer can freely populate). Versioning is bitemporal: `valid_from_commit`/`valid_to_commit` in commit-space (not wall-clock), soft-delete only. Extensibility is a frozen `core@X.Y.Z` profile plus an additive-only `workspace_profile@N`, constrained by SHACL-*shaped JSON* (not full SHACL), where every workspace type's `extends` a core type is mandatory.

### Why

`research-ontology.md` §0's TL;DR and §10 ("Answer to the key question") state this as the document's own bottom line. §1 ("Model choice") is the specific argument against a live RDF/OWL store: RDF has no native edge properties (reification/named-graphs/RDF-star all inflate density and joins for exactly the 8+ properties a soft edge needs), and OWL reasoning "buys us almost nothing here" since AWB's useful inferences are graph traversals, not description-logic entailments. §2.1 (SEON) supplies the structural class set and the pyramid-layering idea that maps directly onto the `layer` column; §2.3 explicitly rejects full-AST-node CPG granularity ("at 'millions of LOC' a CPG is 10^8 nodes... keep AST inside tree-sitter at parse time, persist only declarations + resolved references"). §3 (SKOS) is the specific argument for the soft side: `skos:broader` is deliberately non-transitive and `broader`/`related` are disjoint, which are "load-bearing safety properties" preventing a chain of shaky LLM links from silently entailing a claim nobody asserted. §5–§6 (Provenance, Confidence) supply the PROV-O-mapped, Wikidata-statement-shaped provenance/confidence fields, evidenced by the finding that "LLMs lack provenance or reliability indicators despite extraction capabilities" and that different LLMs given the same text/prompt/schema "produce knowledge graphs that scarcely overlap" — i.e., self-reported confidence is not a measurement, which is exactly why this revision hardened that into a service-layer invariant rather than leaving it as cited background (see Decision). §6.2 is the specific source for the tree-sitter-only 0.75–0.9 discount this revision now separates into two axes (name-resolution vs. runtime-dispatch) rather than one blended number. §9 (Workspace extensibility) is the source of the `extends`-mandatory, SHACL-shaped-JSON, deprecate-never-delete extensibility mechanism.

### Rejected

- **RDF/OWL as the live store** — reification/named-graph/RDF-star overhead for edge properties is the specific, sourced reason (`research-ontology.md` §1); RDF/OWL survive only as an export vocabulary (JSON-LD `@context`), never the queried representation.
- **Full Code Property Graph (AST∪CFG∪PDG) as the persisted model** — CodeOntology's own JDK application produced >2M triples at *method* granularity alone; AWB caps at declaration granularity and never materializes AST nodes as a design rule, not an optimization (§2.2–2.3).
- **OWL classes (with instances) for LLM-derived domain concepts** — would let soft, non-deterministic output contaminate formal reasoning over hard facts; SKOS is chosen specifically because "no formal relationship between SKOS concepts and OWL classes is asserted" (§3).
- **Materializing inverse edges** (SEON's own `invokesMethod`/`methodIsInvokedBy`-style pairs, 68 terms, largely inverse duplicates) — doubles the edge table for no query benefit in an LPG; use two indexes (`(src,type)`, `(dst,type)`) instead (§1 point 3).
- **Full SHACL** (not the SHACL-*shaped JSON* subset) for workspace type constraints — SHACL's own spec explicitly supports being used partially "for a variety of purposes beside validation," which is exactly the shape AWB needs (drives the legend, the inspector form, and the LLM prompt from one source) without adopting the whole spec (§9).
- **Kythe's VName / open-schema hub-and-spoke model** as the identity scheme — requires the instrumented-build extraction Kythe itself requires, already rejected in axis 1; SCIP-shaped `symbol_id` is adopted instead specifically because it's a stable string, not a build-derived artifact (§2.4).
- **A single blended confidence number for both name-resolution certainty and runtime-dispatch certainty** — rejected in this revision; see the `resolution='dynamic'` cap mechanism in Decision above.

### Integration points

- **`apps/server/src/entities/RelationTuple.ts:1-32`** is the closest existing analog — a generic `subject_type/subject_id/relation/object_type/object_id` tuple table with three composite `@Index()`s (currently ReBAC-permissions-only). New `OntologyNode.ts`/`OntologyEdge.ts` entity files should mirror this tuple-table shape for edges and `Resource.ts:8-65`'s flat-column shape for nodes (`scout-server.md` §2).
- **`apps/server/src/entities/index.ts`** — barrel-export the new entities after line 105 (after `OrchestrationEvent`), for TypeScript type-sharing. **On the sql.js backend, these entities are fed to a second `DataSourceOptions` builder, not the primary `entities` array `AppDataSource`/`DatabaseModule` use — see axis 3 for why.** On Postgres, they are fed to the single existing DataSource exactly as originally designed. The "Auto-DDL'd by TypeORM `synchronize`; no hand-written migration needed" comment already standing at `:40-41`, `:43-47`, `:49-51`, `:85-88`, `:97-100` still applies to both DataSources (`scout-server.md` §2). **No migration file is required** — confirmed directly against `db.ts:395-474`, where `synchronize: true` is hardcoded in all three backend branches.
- **`apps/server/src/entities/Ticket.ts:119-126`** (`base_repo_resource_id`/`base_branch`, plain `varchar`, no FK) is the precedent for the `AFFECTS_CODE` bridge edge's ticket-side scoping columns, and generally for how a new entity references "a repository resource + branch" without a DB-level foreign key (`scout-server.md` §1).

## Axis 3 — Storage engine

### Decision

**SQLite (`sql.js`, dev) / PostgreSQL (prod) is the only storage engine — no dedicated graph database, no Kuzu.** A small internal graph-query service (never exposed to agents as free-form SQL) issues `dataSource.query(rawSql, params)` — one hand-maintained SQL variant per dialect, since TypeORM has no recursive-CTE query-builder API on either dialect. Every MCP-exposed traversal is **bounded-depth + path-cycle-guarded + `LIMIT`-capped + confidence-floored by construction, never optional**: `graph_neighbors`/`graph_blast_radius` use a depth-capped (default 3–6 hops), path-cycle-guarded, `confidence >= :confidence_min`-filtered recursive CTE; `graph_call_path` is implemented as **application-orchestrated bidirectional level-BFS with a running visited-set in application memory**, its per-hop frontier query filtered the same way, never a single open-ended recursive CTE. **DuckDB** is adopted today, narrowly, as a **scheduled, read-only, `ATTACH`-based analytics sidecar** (zero-ETL — it reads the same SQLite file or Postgres instance directly) for OLAP-shaped aggregate queries only; its graph-native features (SQL/PGQ, algorithm extensions) are deferred as pre-1.0/community-maintained. **RDF/JSON-LD export** is a streaming serializer (**N3.js** + **jsonld.js**) directly over the relational tables — no embedded triple store. **Embeddings** mirror `ResourceEmbedding` exactly (brute-force JS `cosineSimilarity` as the portable default on both backends); **pgvector HNSW** is an optional, Postgres-only, volume-gated accelerator behind a feature-detected fast path, never a hard backend branch; **sqlite-vec is not adopted.** **The fuzzy-match tier's BK-tree (axis 1) is an in-process JS structure rebuilt/updated alongside Tier 1.5, not a SQLite-level structure of any kind, on either backend.**

**Ontology tables get their own, independently-flushed sql.js DataSource/file in dev — a genuine architecture change, not a footnote (review finding, scale/critical).** `sql.js`'s batched flush (`flushSqljs()`/`doSqljsExport()`, `db.ts:522-566`) is a full synchronous re-export of the *entire* database on a shared, DB-instance-wide dirty flag (`db.ts:61-106`, `SqljsWriteSubscriber` — set by any non-`SELECT`/`PRAGMA` write anywhere in AWB) on a shared periodic cadence (`db.ts:578-588`, default 30 s): `dataSource.sqljsManager.saveDatabase()` → the driver's own `db.export()` → `fs.writeFileSync(location, out)` (confirmed `db.ts:560`, `db.ts:763`), on the WASM main thread. At this design's own 10 MLOC projection (~100k–150k aggregate nodes plus the ~240k–800k aggregated edge rows §6.3 below sizes), `OntologyNode`/`OntologyEdge` can plausibly add tens to hundreds of MB to whatever file they share. If they shared the *primary* `data.db` — the default outcome of simply barrel-exporting them per axis 2's own stated integration point — every subsequent flush, triggered by an unrelated ticket comment or SSE log line anywhere in AWB, would re-serialize and rewrite the enlarged file synchronously, **blocking the entire instance's request handling for every user, not just ontology-graph users**, on a recurring cadence for the life of the process. This ticket (`d5a8594a`) already fixed the *frequency* of this exact failure mode once; nothing before this revision addressed the *per-flush cost* growing unboundedly with a new, potentially very large table family. **Fix, decided here**: ontology tables are persisted through a **second `DataSource` instance** (a second in-process sql.js/WASM instantiation, a second on-disk file, e.g. `database/ontology.db`) with its **own** dirty flag, its **own** flush timer, and its **own** `serializeSqljsTransactions()` queue (see below) — never sharing any of the three with the primary OLTP DataSource. This is dev/sql.js-only, gated the same way every other batched-flush mechanism already is (`isSqljsBackend()`, `db.ts:36-38`) — **Postgres is a single DataSource, ontology tables alongside everything else, exactly as originally designed**, since Postgres has no full-file re-export step to inflate in the first place. This is a **partial**, not complete, fix and is stated honestly as such: the ontology DataSource's *own* flush is still a full synchronous re-export when it fires, so one large workspace's ontology growth can still slow *other* workspaces' ontology-graph flushes (though never the rest of AWB). Two further, deliberately scoped mitigations close the residual risk: (1) a **row-count ceiling** (`ONTOLOGY_SQLJS_ROW_CEILING`, default TBD — see benchmark requirement below) above which the feature degrades to read-only-against-last-snapshot or is disabled for that workspace on the sql.js backend, rather than silently growing an unbounded export cost — Postgres has no such ceiling; (2) an explicit **rejection**, not adoption, of "move the flush off the main thread" as a v1 mechanism: `sql.js`'s WASM-resident `Database` object is not a structure a `worker_threads` boundary can safely share without redesigning flush ownership, which this document does not size here — it is a real, documented follow-up (§10a), not a v1 commitment. **Before this ships, a child ticket must measure actual `db.export()` wall-clock time at this design's own projected row counts on the real pinned `sql.js` build** — no document in this corpus, including this one before this revision, ever measured that number, and the row-count ceiling's actual default depends on it.

**A direct, positive side effect: this also resolves the transaction-serialization contention finding below, for free.**

**`serializeSqljsTransactions()`'s FIFO queue is per-DataSource, and ontology bulk writes must still minimize call count within their own queue (review finding, scale/major).** `serializeSqljsTransactions()` (`db.ts:159-186`) FIFO-queues every `dataSource.manager.transaction()` call across one sqljs DataSource, because sql.js has exactly one WASM connection/query-runner per DataSource (the fix's own comment at `db.ts:108-158` explains the shared-runner race it closes). Prior to this revision, ontology bulk writes (initial 280k+ node population, Phase B's fan-out burst — which `research-incremental.md` §5.4 itself says can hit reverse-index fan-in "in the thousands" for a hot symbol at target scale) would queue behind, and block, *every* concurrent transactional write elsewhere in AWB (ticket moves, comments, agent-dispatch bookkeeping) on the single shared DataSource, and vice versa. **The dual-DataSource fix above already isolates this** — `serializeSqljsTransactions(ontologyDataSource)` is called once at construction exactly like the primary's (`db.ts:481`'s pattern), giving ontology writes their own independent FIFO queue that no longer contends with ticket/chat/dispatch writes. This does not, by itself, make the ontology DataSource's *own* queue efficient: one `transaction()` call per file or per batch during bulk population still serializes ontology-internal writes behind each other unnecessarily. **Decided here**: ontology bulk writes must minimize the *number* of `transaction()` calls (large batched inserts per extraction run, or raw `dataSource.query()` outside the transaction manager for pure-insert phases) rather than just minimizing total row count — and a child ticket must measure the expected wall-clock duration a full-repo initial population run holds the ontology DataSource's own queue, the same way the flush-cost benchmark above is required before shipping a default.

### Why

`research-storage.md` exists specifically to validate — not re-decide — the relational choice `research-ontology.md` already made, and its own §0 TL;DR states the bottom line: bounded traversal is safe on both engines; unbounded shortest-path as a single query is not, on either engine. §2.1–2.3 supply the mechanical reason: SQLite's own docs note a recursive-CTE step "cannot see whether a *different* branch of the recursion has already visited a node" (Keith Medcalf, SQLite forum), and DuckDB's own engineering writeup quantifies the consequence — a **424-node** toy graph produces **605.9M rows** and an out-of-memory crash under vanilla recursive-CTE semantics, because standard `UNION ALL` recursion has no cross-path "already settled" memory. §3 confirms this is dialect-agnostic with a **real production incident**: GitLab's own `WITH RECURSIVE "namespaces_cte"` query dominated `pg_stat_statements` and drove a Sidekiq slowdown. §4 grounds the DuckDB decision in its one genuinely killer feature — zero-ETL `ATTACH` against the *same* SQLite file or Postgres instance AWB already runs, no second consistency domain — while §4.2 documents why its graph-native SQL/PGQ layer is explicitly not ready ("not available in the latest DuckDB release," every example ETLs into DuckDB's own tables, defeating the zero-ETL point). §6.1 is the specific, author-confirmed reason sqlite-vec is off the table: "It's not possibl[e] to dynamically load a SQLite extension into a WASM build of SQLite" — AWB's dev backend (`sql.js`, confirmed against `db.ts`) is exactly such a build, so sqlite-vec would require forking `sql.js`, a real ongoing dependency-tracking cost not justified by the projected ~100k–150k aggregate-node embedding volume (§6.3) — **this revision applies the identical reasoning to reject FTS5 for the fuzzy-match tier, for the same underlying reason** (axis 1). §7 corroborates the whole approach by comparison: every serious code-intelligence system surveyed (Sourcegraph, CodeQL, Glean) either uses relational storage plus one narrow specialized add-on for exactly one hot workload, or accepts an operational cost class (RocksDB+Thrift+Haskell, a bespoke Datalog evaluator) AWB's multi-tenant, TypeORM-integrated, no-dedicated-ops-team reality doesn't support — AWB's shape (relational core + DuckDB sidecar) is "the industry-standard shape, not a compromise." The dual-DataSource decision above is new to this revision and is not sourced from prior research (no document anticipated it) — it follows directly from re-reading `db.ts`'s own already-documented flush mechanism (ticket `d5a8594a`) against this design's own projected row counts, which no prior revision of this document did.

### Rejected

- **KuzuDB** — the embedded Cypher graph DB most 2025-era code-graph blog posts recommend, **archived 2025-10-10** after an Apple acqui-hire of the team; explicitly ruled out (`research-extraction.md` §0, §5.2: "Do not pick Kuzu").
- **A single unbounded recursive-CTE shortest-path query** for `graph_call_path` — not "slow," but "essentially certain to exhaust memory" at AWB's 280k-node target, per the row-explosion evidence above; the fix (bounded, leveled, application-orchestrated BFS) is structural, adopted from day one (§2.3–2.4).
- **Precomputed full transitive closure** (even via SQLite's own official `ext/misc/closure.c` extension) — right idea for hierarchical *containment* (a tree), wrong for the reference/call graph, which is cyclic and O(n²) worst-case at realistic fan-out; also a loadable C extension, so unavailable under `sql.js` anyway (§2.5).
- **DuckDB SQL/PGQ / DuckPGQ as a live traversal engine** — real and converging, but pre-1.0, community-maintained, not compatible with the latest DuckDB release at research time, and every documented usage pattern requires ETL'ing into DuckDB's own tables — deferred, not adopted, until it stabilizes into an ATTACH-compatible, non-community feature (§4.2, §4.5).
- **Oxigraph** for RDF export — its own README states the JS/WASM binding is "a work in progress," in-memory-only, with `LOAD` unsupported; no benefit over direct N3.js/jsonld.js serialization for a one-shot export of an already-materialized relational graph (§5).
- **sqlite-vec** — WASM extension-loading is architecturally impossible without forking `sql.js` (§6.1); not adopted now, revisit only if measured embedding volume or an upstream WASM-loading fix changes the calculus.
- **SQLite FTS5 for the fuzzy tier** — not compiled into `sql.js`'s default distribution; would require the same fork-`sql.js` cost class as sqlite-vec, for a smaller payoff (axis 1). Rejected for consistency with the sqlite-vec decision, not merely because it happens to be unavailable.
- **RocksDB** (Glean's choice) and a **bespoke Datalog evaluator** (CodeQL's choice) as alternative storage architectures — right for Meta's monorepo-scale immutable fact stream and GitHub's compliance-grade batch whole-program analysis respectively, wrong for AWB's per-workspace, multi-tenant, TypeORM-joined, live-incrementally-updated requirement (§7.2–7.3).
- **Moving the sql.js flush off the main thread as a v1 mechanism** — real, and a legitimate follow-up, but `sql.js`'s WASM `Database` object cannot be safely handed across a `worker_threads` boundary without a flush-ownership redesign this document does not size; deferred (§10a), not adopted now.
- **Per-workspace or per-graph sql.js files** (as a further escalation past the single shared ontology DataSource) — would fully close the residual "one workspace's ontology growth slows another workspace's ontology flush" risk, but at a real, ongoing operational cost (N open WASM instances, N flush timers) `research-prior-art.md` §6 pitfall #4's small-team maintenance-burden ceiling argues against committing to unconditionally; the row-count ceiling is adopted as the v1-sized response instead, with this escalation path documented (§10a) if the ceiling proves too restrictive in practice.

### Integration points

- **`apps/server/src/db.ts:28`** (`Object.values(entitiesBarrel)`, feeding `buildDataSourceOptions()`'s `entities` field at `:408,446,468`) is the pattern a **new, sibling `buildOntologyDataSourceOptions()`** function copies for the sql.js backend — scoped to only the `Ontology*` entities, `location` pointed at a second file, its own `subscribers: [OntologySqljsWriteSubscriber]` (a clone of `SqljsWriteSubscriber`, `db.ts:95-106`) and its own dirty flag/flush timer. On Postgres/MySQL, ontology entities are simply included in the existing single `entities` array — no second DataSource is constructed on those backends. `synchronize: true` remains hardcoded on every branch, confirmed at `:410` (mysql), `:448` (postgres), `:470` (sqljs default) (`scout-server.md` §2).
- **TypeORM's missing recursive-CTE builder** (confirmed via `research-storage.md` §1 against TypeORM issues #1116/#10731, both still open/PoC) means the graph-query service must use `dataSource.query(rawSql, params)` directly — the same raw-repository-access pattern already proven for `Resource` (`resource-tools.ts:32`) and `DispatchIntent` (`manager.getRepository(DispatchIntent)` in `dispatch-intent.service.ts:174`), neither of which required `TypeOrmModule.forFeature` (`scout-server.md` §2 point 4). **On sql.js, this raw-query call must target the ontology DataSource, not the default-injected one** — the graph-query service takes its `DataSource` as an explicit constructor parameter rather than relying on NestJS's default DI token, so it can be wired to either DataSource per backend.

## Axis 4 — Incremental-update algorithm

### Decision

A **four-mechanism pipeline**, in priority order, all already anticipated by `research-ontology.md`'s schema (`symbol_id`, evidence-hash staleness) and made concrete here:

1. **Stable, content-addressed `symbol_id` identity** (already decided in axis 2) as the precondition every other mechanism depends on.
2. **Signature/body-split early cutoff**: a new `signature_hash` column (name, kind, arity, visibility, param/return types, heritage — excludes the body) computed alongside the existing `content_hash`. A body-only edit changes `content_hash` but not `signature_hash`, and refresh **stops immediately** — no other file is touched.
3. **A materialized reverse-dependency index** — `reverse_edge_index(dst_symbol_id, src_file_id)` — walked *only* when a symbol's `signature_hash` actually changed, added, or was removed **— or when its file was renamed/moved (new trigger, see below)** — file-level lookup first (bounded by file count) and symbol-level second (bounded by reference count), never a full transitive walk.
4. **Durability tiers** — `volatile` (workspace source) / `stable` (lockfile-pinned deps) / `frozen` (vendored/generated, `is_generated`) on `File`/`Repository`/`ExternalPackage` nodes — a commit touching only `volatile` files **never issues** the reverse-index walk against `stable`/`frozen` partitions at all, not "walks and finds nothing."

Composed into a concrete **Phase A/B/C** algorithm run on every debounced file save (and, with identical logic, on a `git diff <last_indexed_commit>..HEAD --name-status -M` scoped batch on branch switch/large external edits): **Phase A** (always) re-parses the changed file, diffs by `symbol_id`, computes `signature_hash` — stop here on no signature change **and no rename** (see below). **Phase B** (on signature change, or unconditionally on a detected rename/move, see below) queries the reverse index and re-runs the Tier-1.5 resolver for the affected files' *outgoing* edges only. **Phase C** (lazy) flips stale `semantic`/`derived` edges by evidence-hash mismatch — never a synchronous re-summarization. A **separate background sweep**, decoupled from the save path, drains the stale queue under a priority order (open folder → active-ticket folder → centrality), a per-sweep batch cap, and a per-node cooldown, using the Anthropic Batch API (50% off) and prompt caching for the bottom-up ancestor-chain summarization Tier 3 needs.

**Rename/move is now an explicit, unconditional third Phase-B trigger — closing a silent, permanent correctness gap (review finding, integrity/critical).** A prior revision's rename handling ("rename detection updates the existing `File` node's path in place, preserving its `symbol_id`s") only prevented `symbol_id` churn — it never re-triggered Tier-1.5 resolution for the *moved file's own outgoing edges*. Phase A's early-cutoff gate is keyed on `signature_hash`, a pure function of the file's own declared symbol shapes; a pure rename/move changes neither `file_content_hash` nor any symbol's `signature_hash`, so Phase B never fired for it — confirmed against `research-incremental.md` §6's own R100 handling, which describes only "update the existing File node's path in place... rather than soft-deleting and re-inserting," with no mention of re-resolving that file's `refs[]`. But two of Tier-1.5's cascade tiers are inherently path-relative — same-module (0.90) and import-suffix (0.85) — resolving based on the calling file's location relative to candidate targets. A file moved to a new directory with byte-identical content can have its relative-import resolution targets silently shift (e.g. a same-named sibling now closer) while every staleness signal (`content_hash`, `signature_hash`, `evidence_ref` hash) reports "unchanged" — and the background stale-queue sweep is itself evidence-hash-driven, so it would not catch this either. A stale/wrong edge from the moved file would survive indefinitely. **Fix**: Phase A's rename branch (git `-M` detection, already run for path-update purposes) now unconditionally re-runs the Tier-1.5 resolver for the moved file's own outgoing `refs[]`, regardless of `signature_hash`. Cost is bounded (one file's reference list); the correctness gap it closes was otherwise silent and permanent.

**The background sweep is a cost cap, not a staleness-convergence guarantee — surfaced honestly rather than assumed (review finding, scale/major).** The sweep's three throttling knobs (sweep interval, per-sweep batch cap, per-node cooldown; `research-incremental.md` §5.2) are deliberately sized to cap *cost*, not to track staleness *arrival rate*. `research-incremental.md` §5.4 itself establishes that in-degree in real code graphs follows a power law and that fan-in "in the thousands" for foundational symbols is realistic at the multi-MLOC scale this feature targets — continuous multi-contributor edit activity on a large active repo will continuously flip a nontrivial fraction of the semantic layer's evidence hashes to stale. No document anywhere in this corpus models the steady-state relationship between arrival rate (edit velocity × fan-out-to-ancestor-chain) and the capped drain rate, and this revision does not invent that model retroactively — doing so honestly requires real telemetry this design did not have before. **What this design commits to instead**: (1) explicitly not claiming drain-rate convergence at any specific scale target without that data; (2) surfacing staleness honestly at both consumption points — every MCP response's `{indexed_at, confidence}` (already mandated) and the UI's new persistent freshness badge (axis 5) — rather than implying eventual freshness; (3) a telemetry Done-when on child ticket #6 (axis 6) to log stale-queue size/age percentiles per workspace over time, so a future revision of this document can size the budget against real arrival-vs-drain data instead of guessing.

**The "sub-second" headline claim is now scoped to the case it actually covers (review finding, scale/minor).** The bottom-line-up-front and this axis's own prior text claimed the incremental pipeline "keeps a single-file edit sub-second" without qualification. `research-incremental.md` §5.3's "sub-second" language is scoped to a generic single-file Phase A/B pass and does not cover the case its own §5.4 flags as realistic at scale: "a genuine signature change to a hot symbol" whose reverse-index fan-in "will legitimately have... fan-in in the thousands" once the repo reaches the multi-MLOC range this feature targets — Phase B for that case re-runs the Tier-1.5 resolver against every one of those files' outgoing edges, and no document anywhere estimates that case's actual latency. **Fixed here**: the claim is now explicitly qualified — sub-second for the common case (body-only edits, and signature changes with typical, non-hot-symbol fan-in); hot-symbol signature changes at realistic multi-thousand fan-in are an explicitly separate, unmeasured case, treated as a debounced/background-priority path, not covered by the sub-second SLA, until a child ticket benchmarks it.

### Why

`research-incremental.md`'s own §0 TL;DR and "Bottom line up front" state that every production system solving this problem — rust-analyzer/salsa, TypeScript's `tsserver`, GitHub's CodeQL, Meta's Glean, and the Bazel/Buck2/Turborepo/Nx build-cache family — converges on the same four mechanisms in the same priority order, and that AWB already has (1) and a version of (3); this document supplies the concrete reverse-index/durability design that was missing. §1.1 (rust-analyzer) is the direct source for the signature/body split: its `ItemTree` — "a stable summary of a syntax tree" decoupled from function bodies — is why "typing inside a function's body never invalidates global derived data," which §4.2 concretizes into AWB's `signature_hash` column. §1.3 (CodeQL) is the single strongest evidence for why stable identity is a *precondition*, not a nicety: on a real production codebase, "the average impact of a commit on the EDB was ~4 million tuples — larger than the EDB itself — irrespective of how small the actual code change was," traced directly to sequential/counter-based ids; fixing identity dropped the change rate "to at or below 5% for commits touching up to 1000 lines" — this is also the direct precedent this revision leans on for why the rename gap above was serious enough to fix unconditionally rather than defer: unstable resolution context is the same class of bug as unstable identity, just triggered by a move instead of a rewrite. §3 (Nx `affected`, Buck2 DICE's `rdeps`) is the source of the reverse-index design — "O(invalidated subset) traversals and O(changed subset) recomputations" — and specifically Nx's coarse-then-fine, file-level-then-symbol-level ordering. §4.3 (durability) is rust-analyzer's own fix for the residual cost a pure red-green scheme still pays. §5 (batching/priority/debounce) is the concrete scheduler shape, independently corroborated by Sourcegraph's own auto-indexer using the identical three-knob (interval/batch-cap/cooldown) design for a different tier of a comparable pipeline (`research-prior-art.md` §1.1) — and §5.4's power-law fan-in finding is exactly the evidence this revision now treats as a live risk to the sweep's convergence claim, rather than only as a reason Phase B's *cheap* resolver re-run (not the *expensive* Tier-3 re-summarization) is the thing that scales with fan-in.

### Rejected

- **"Fully incremental" everywhere** — CodeQL's own fully-incremental prototype needed **>1 hour to initialize and ~70 GB of memory**, versus a hybrid design (non-recursive parts recomputed from scratch on the bounded changed-input set) at ~15 minutes / ~20 GB with the same commit-size-proportional update guarantee (`research-incremental.md` §7 trap #1). AWB's Tier 1 (cheap enough to redo from scratch on the changed-file set) / Tier 1.5 (incremental via the reverse index) / Tier 2–3 (explicitly batch/lazy, never live-incremental) split *is* this hybrid shape; making Tier 2 or 3 "live" to chase lower latency is explicitly rejected as scope creep the evidence argues against.
- **A deep constructive trace (single flat content hash, Turborepo/Nx-task-hash style) for Tier 3 LLM output** — correct and excellent for Tier 1's deterministic file-level re-parse decision, but Build Systems à la Carte's own caveat is that a flat hash-of-everything cache is only *correct* for deterministic computations, which an LLM call is not, and it forecloses the fine-grained early cutoff a sibling-summary cache needs (§7 trap #2).
- **Naive "mark every file that could possibly reference it as needing full re-extraction"** on a hot-symbol edit — this reproduces CodeQL's own O(repo)-not-O(change) failure mode at the AWB-schema level; the fix is the signature/body split plus the durability pre-filter, not a bigger cache (§7 trap #3).
- **Treating a rename as delete+insert** (a naive `git diff` without `-M`) — manufactures the same churn unstable ids do, at the git-integration layer instead of the id-assignment layer; rename detection updates the existing `File` node's path in place, preserving its `symbol_id`s (§7 trap #4). **Extended in this revision**: preserving the path alone is necessary but not sufficient — the unconditional re-resolution branch above closes the gap that left preserving-the-path as an *incomplete* fix.
- **Claiming sweep convergence at a specific scale target without arrival-rate data** — rejected in this revision; see the honest-surfacing decision above.
- **Differential dataflow as a standing streaming runtime** — the "asymptotically ideal" general solution (every derived fact automatically, incrementally maintained by key, no manual reverse-index walk), but adopting it means running a second, always-on compute engine alongside NestJS+TypeORM — a much bigger operational bet than warranted; the *key-indexed delta-propagation principle* is borrowed instead, implemented as a plain indexed SQL query (§3).
- **Eager recompute of every derived/semantic consequence of a structural change** — Adapton's demand-driven caution: mark `stale` (cheap), only actually recompute what an MCP call or UI open event *demands*, matching the LazyGraphRAG tradeoff `research-ontology.md` §4.2 already adopted (§4.4).

### Integration points

- **`apps/server/src/modules/mcp/shared/git-repo-cache.ts`**'s `countBehindAhead()` (`:701-721`), `mergeBase()` (`:732-746`), and `diffChangedPaths()` (`:769-784`) — already used by the review-drift merge gate against validated refs on the same cache clone — are the exact reusable primitives for computing the `git diff <last_indexed_commit>..HEAD --name-status -M`-scoped reindex trigger (rename detection included, feeding the unconditional-re-resolution branch above) and for an "is this graph stale relative to HEAD" freshness check feeding the UI badge (axis 5), rather than reimplementing git diffing from scratch (`scout-server.md` §3b).
- **New columns, not new tables, for most of this**: `signature_hash` on `Callable`/`Type`/`Field`, `durability` on `File`/`Repository`/`ExternalPackage`, plus two small dedicated tables (`reverse_edge_index`, `enrichment_queue`) — all additive `@Column()`/new-entity changes, auto-DDL'd by the same `synchronize: true` path verified in axis 2/3 (`db.ts:395-474`), zero migration file required (`scout-server.md` §2). On the sql.js backend these land in the ontology-only DataSource (axis 3).
- **Progress reporting during a refresh** reuses the exact SSE pattern already proven for a comparable "N processed so far" counter: `apps/client/src/components/AgentSubagentsPanel.tsx:74-85`'s direct-increment pattern (`useBoardStreamEvent('subagent_log', ...)` incrementing local state without a refetch) is "the closer fit" for a `{workspace_id, job_id, edges_extracted, edges_total, ...}`-style progress frame than the refetch-on-signal pattern `MissionDetailPage.tsx` uses (`scout-client.md` §3.4). Wiring it requires one new literal on `StreamNamedEventType` (`BoardStreamContext.tsx:34-46`) and one `eventSource.addEventListener(...)` block in `connect()` (`:153-224`, pattern at `:216-218`) — per `CLAUDE.md`'s Agent Manager sync rule, this SSE-contract change ships server + client in the same PR. **The same progress-frame shape now also carries `graph_status`'s `building`/`ready`/`stale`/`error` state (axis 6), rather than inventing a second event shape for the lifecycle tool.**

## Axis 5 — Rendering stack

### Decision

**Two rendering engines behind one interaction model, not one engine for everything.** The default view is **sigma.js + graphology + `@react-sigma/core`** (WebGL 2D) rendering the aggregated `Community`/`Module` view — `nodeReducer`/`edgeReducer` plus `camera.ratio` are the literal implementation mechanism for semantic zoom, mapped onto the node-type hierarchy (`Community` → `Directory`/`File`/`Module` → `Type`/`Callable`/`Field`/`Endpoint`/`DataEntity` as the camera zooms in). **cosmos.gl via `@cosmograph/react`** is a deliberate **opt-in** raw/expanded mode for when a user explicitly drills past the aggregated view's scale. **Community detection uses `graphology-communities-leiden`, never Louvain.** **Layout stability is a position-persistence contract, not a layout-algorithm feature**: store each node's last converged `(x, y)` keyed by its stable `symbol_id`, reseed unchanged nodes at their old coordinates with `fixed=true` so ForceAtlas2 only moves new/changed nodes, and animate the transition with `animateNodes`. **Focus+context** ("Expand a node's N-hop neighborhood") is a thin UI layer over the **identical bounded-BFS backend** axis 3/6 already define for `graph_neighbors`/`graph_blast_radius` — not a second, independently-tuned implementation — defaulting the very first render of any graph to a **20–50 node** budget.

**The sigma.js-as-unconditional-default is now gated on a pre-ship measurement, not shipped on an unverified assumption (review finding, scale/critical).** A prior revision's safety net for the default (non-opt-in) render path staying under sigma.js's own measured ~5,000-node collapse point rested entirely on one explicitly-hedged sentence: the aggregated view of a 10 MLOC repo "collapses ~280k definition nodes into what is **very likely** hundreds to low thousands of Community/Module/File meta-nodes after Leiden clustering" (`research-visualization.md` §2.5). No document in this corpus ever reports an actual resulting community *count* for any real code graph at this scale — the cited indexing-speed numbers (Django 49,398 nodes, Linux kernel 2.1M nodes) measure node/edge counts, never how many communities resulted. `research-ontology.md`'s own schema already supports a hierarchical fix (`Community(level, algorithm='leiden', parent_community_id, size, cohesion)`) — but `research-visualization.md` §4.8's actual rendering algorithm treats `Community` as one flat single-level tier ("all the way out → `Community`/`Module` only") with no logic to walk `parent_community_id` up to a coarser level, and Leiden's own refinement phase tends toward fairly small, cohesive communities on real modular structure — if average community size at 280k nodes is in the tens rather than hundreds, single-level community count could land at 5,000–15,000, already past sigma's ceiling on day one, with cosmos.gl's opt-in mode explicitly scoped for "more detail," not "even the aggregated view is too big." **Fixed here, two ways**: (1) a child ticket must measure actual Leiden community count/size distribution on a real large (multi-MLOC) repo before sigma.js's *unconditional* default status ships; (2) the render tier is made explicitly budget-aware regardless of that measurement's outcome — `graphology-communities-leiden`'s hierarchical output (`level`/`parent_community_id`, already schema'd) is walked from the finest level upward until the node count at that level drops under a fixed render budget (~2,000 nodes), not rendered at a single fixed level — with a defined fallback (a paginated community list, or a second coarsening pass) if even the coarsest level still exceeds sigma's ceiling. This makes the "does the default fit in sigma.js" question self-correcting at query time instead of resting on one hedged sentence.

**Layer and confidence are now visually encoded, not only queryable (review finding, integrity/major).** `research-ontology.md` §8.7 proposed this directly — "solid = structural, dashed/translucent = semantic, gold = curated" for `layer`, and `confidence` as opacity — "separability must be visible, not just queryable." A prior revision's axis 5 never carried this into its actual Decision/Integration-points text; the only committed palette guidance was `tokens.colors.{...}` for node-*kind* categorical color, with zero mention of layer or confidence, meaning a human looking at the default aggregated view had no way to tell a 0.35-confidence fuzzy `CALLS` edge from a 1.0-confidence SCIP edge on screen. **Fixed here**: `edgeReducer` maps `layer` to line style (solid = `structural`, dashed = `derived`/`semantic`, a distinct gold-toned dashed stroke = `curated`, per `research-ontology.md` §8.7's own scheme) and `confidence` to opacity (roughly linear, `0.35` confidence → ~40% opacity, `1.0` → 100%) on every rendered edge — a visual expression of the same honesty discipline the MCP contract already enforces textually (axis 6). Added to child ticket #8's scope.

**A persistent UI freshness badge is now a mandatory axis-5 decision, not an implicit assumption or a footnote in a different document (review finding, adoption/critical).** `research-prior-art.md` §6 pitfall #5 — which this document's own preamble already says shapes its adoption-risk stress test — states directly that "the `dirty_ratio`/staleness marker... must be visible at the point of consumption... not only in a UI corner a human might never look at." A prior revision faithfully implemented the *agent-facing* half (every MCP response already carries `{source, confidence, indexed_at, commit}`) but never implemented the *human-facing* half: axis 5 had zero mention of a staleness/freshness indicator anywhere in the sigma.js UI, and the only place a UI staleness label was even mentioned in this corpus was a narrow DuckDB-sidecar footnote in `research-storage.md` — never promoted into an actual axis-5 decision or child-ticket scope. This is exactly the scenario pitfall #5 calls fatal if silent: "a graph that looks authoritative but is quietly wrong is worse than no graph, just grep." **Fixed here**: a persistent badge/banner on the graph view, reusing `research-ontology.md` §8.6 point 6's own already-specified `dirty_ratio` field and UI copy pattern ("graph is 96% fresh as of `<sha>`"), computed via the `countBehindAhead()` primitive axis 4's integration points already cite, showing `indexed_at` commit vs. current HEAD. Stated as a Done-when item on child ticket #7 (route/chrome — the badge's natural home even before the full rendering engine ships, so freshness is visible starting from the route skeleton) rather than an implicit assumption.

**Child ticket #8 (the rendering engine itself) is now gated behind a measured usage signal, resolving an internal inconsistency (review finding, adoption/major).** §10a item 3 states a human-browsable UI "is real work, not deferred," but is not the feature's adoption bet — while §10a items 1, 2, and 5 (SCIP/LSP, `graph_search_symbols`, `graph_hotspots`) are all explicitly gated behind demonstrated MCP-tool value before they ship. Ticket #7 (route/chrome skeleton) and ticket #8 (the actual sigma.js/graphology/Leiden canvas — a brand-new client dependency and a full 2D/WebGL rendering stack, real engineering effort comparable to or larger than the deferred MCP tools) carried no equivalent gate in a prior revision, scheduled unconditionally alongside wave-1 tools — which, if the UI genuinely isn't the adoption bet, contradicts that by building the exact "destination view" surface `research-prior-art.md` §2.4/§3.4 says killed CodeSee/Sourcetrail, without first confirming the MCP tools it's supposed to be secondary to are actually used. **Fixed here**: ticket #7 (cheap — route, sidebar entry, tokens, chrome, and now the freshness-badge home above) ships in wave 1 alongside the MCP tools; ticket #8's actual rendering-engine build is gated behind the same measured-recurrence signal axis 6 now requires wave-1 MCP tools to log from day one (axis 6 "Graph lifecycle & adoption evidence") — the same bar already applied to `graph_hotspots`/`graph_search_symbols`, now applied consistently to the human UI too.

### Why

`research-visualization.md`'s own bottom-line-up-front states this two-tier engine split as the answer, and §2.3's six independent, primary-sourced benchmark data points verify (not assume) the specific ceilings `research-ontology.md` §8.7 had asserted without citation: sigma.js issues #239 (2014) and #567 both document real struggle around **~5,000 nodes**, with #567's specific finding — disabling edge *rendering* didn't help — proving the bottleneck is the **layout simulation**, not the renderer, so no amount of visual tuning fixes it; Graphify's own production postmortem (#447) rejects an 8,333-node graph outright and lists "aggregated view first, switch to sigma.js/Cosmograph second" as its own fix ladder, independently arriving at the exact architecture AWB already committed to; Stanford CESTA reports "a network with seven thousand nodes and 166,000 edges brought Sigma.js to its knees"; cosmos.gl clears **1M+ nodes/links** on real (non-synthetic) production datasets per the OpenJS Foundation's own framing and Nightingale's three concrete dataset measurements. §3 grounds the layout-stability mechanism in three independently-converging implementations (graphology ForceAtlas2's `fixed` attribute, `graphology-layout-force`'s `isNodeFixed`, d3-force's `fx`/`fy`) all exposing the identical seed-plus-pin primitive, plus real, felt evidence this matters: Obsidian's graph view has an open, multi-year "Save Node Positions" feature request and an unofficial community-built workaround plugin specifically because it lacks this. §5.1–5.2 is the specific, evidence-grounded reason Leiden replaces Louvain: Traag/Waltman/van Eck's 2019 paper proves Louvain can produce **internally disconnected** communities (up to 16% in the algorithm's own validation) — a `Community` node rendered as one visual blob is "the graph... lying about relatedness at exactly the tier most users will look at first," the same class of trust failure `research-ontology.md` §6 built an entire confidence/provenance system to prevent for LLM edges, just arriving via a purely algorithmic path; NVIDIA's cuGraph benchmarks show Leiden at **3.05–4.14 s on a 3.8M-node/16.5M-edge graph** versus CPU Louvain-class ~145 s. §6.2–6.3 grounds focus+context in Neo4j Bloom's production "Expand"/"Advanced Expansion" pattern and the yFiles knowledge-graph guide's concrete 20–50-node initial-render number. `research-ontology.md` §8.7 is the direct, previously-uncarried-forward source for both the layer/confidence visual encoding and the freshness badge, both fixed in this revision. `research-prior-art.md` §6 pitfalls #1, #5, and #8 are the direct sources for the ticket-#8 usage gate: never a standalone destination view (#1), never let staleness be invisible (#5), and measure re-opens/recurrence, not first-opens (#8) — a rendering engine shipped unconditionally, with no freshness signal, ahead of any recurrence evidence, would have quietly violated all three at once.

### Rejected

- **Louvain for community detection** — the connectivity defect is the specific, sourced disqualifier, not a speed preference; Codebase-Memory (AWB's own closest analog) shipped plain Louvain with a hand-rolled density-based refinement workaround, which is itself evidence the defect is real enough to need mitigating even by a system that didn't fully solve it (§5.3) — AWB uses the algorithm that doesn't need a workaround.
- **cosmos.gl as the default/sole engine** — its per-element styling model is coarser (no `nodeReducer`-equivalent), and its layout-stability primitive is strictly weaker: `disableSimulation` seeding is "init-time only," with no documented per-node pin analogous to graphology's `fixed` attribute (§3.3) — accepted only for the opt-in raw mode, where more positional drift is an explicit, disclosed tradeoff, not the default experience.
- **sigma.js for raw/expanded mode past its measured ceiling** — issue #567's finding (disabling edge rendering didn't help) proves the fix at that scale is architectural (switch which engine does the *layout*), not tunable; tuning sigma.js harder is explicitly rejected as the response to scale pressure (§8 trap #2).
- **`reagraph`** as the primary rendering library — has built-in Expand/Collapse, which is attractive, but adopting it as primary would mean a third rendering paradigm (Three.js) alongside sigma.js/cosmos.gl's WebGL-2D/GPU-shader split; kept as a fallback to *evaluate only if* building Expand on sigma.js's lower-level primitives proves too slow (§6.5).
- **GitHub's "dependency graph" and Gource as prior art to build on** — both are natural-sounding false leads verified and rejected on inspection: GitHub's feature is a flat tabular list, not a zoomable node-link view; Gource is a git-history replay tool with no cross-file reference-edge concept at all (§4.4–4.5). Neither transfers as rendering-technique prior art (though Gource's tree-as-branches visual grammar is worth stealing narrowly for the structural containment layer).
- **Rendering the raw graph directly, at any point** — reaffirms `research-ontology.md` §8.7 and `research-extraction.md` trap #5's "never render raw edges" mandate; the aggregated Community/Module view is the default and the first thing rendered, full stop.
- **Shipping the sigma.js rendering engine (ticket #8) unconditionally in wave 1** — rejected in this revision for internal consistency with how every other speculative-value feature in this design (§10a items 1/2/5) is already gated; see Decision above.
- **A single fixed community-detection level as the render tier** — rejected; the budget-aware walk up `parent_community_id` (Decision above) replaces it specifically because a fixed level's fitness under sigma's ceiling was never verified.

### Integration points

- **No canvas, WebGL, or graph-rendering library exists anywhere in `apps/client/`** today (`grep -rln "canvas\|Canvas" src` → no real hits; zero `d3`, `cytoscape`, `sigma`, `vis-network`, `reactflow`, `three` in `apps/client/package.json`) — confirming this is a fully greenfield client dependency, not a partial rebuild (`scout-client.md` §4).
- **`apps/client/src/tokens.ts`** (the single, full 111-line source of every color/spacing/radius/shadow value in the client — there is no CSS file, no `:root` custom property anywhere) is where the node/edge categorical palette must come from — `tokens.colors.{accent, accentViolet, success, warning, danger, info}` (already the app's categorical status/badge palette) for node-kind colors, `border`/`borderStrong` for edges, plus the new layer/confidence `edgeReducer` mapping above — validated for accessible contrast against `surface`/`surfaceCard` via the existing `contrastRatio()` helper in `apps/client/src/utils/contrast.ts:33-38`, rather than hand-picked hex literals (`scout-client.md` §2).

## Axis 6 — MCP tool surface

### Decision

Ship **six-to-seven `graph_`-prefixed MCP tools total, in three ordered waves**, built strictly *on top of* — never duplicating — the three fixed, bounded-traversal tools `research-storage.md` already named (`graph_neighbors`, `graph_blast_radius`, `graph_call_path`).

**Graph lifecycle & discovery (new subsection — folds a would-be seventh axis into axis 6, per this document's own 6-axis structure) (review finding, adoption/critical).** A prior revision assumed an `OntologyGraph` row and `graph_id` already exist for every axis-6 tool, including `graph_find_symbol`, whose own schema requires `graph_id` as input with the description "see the graph you last built/refreshed for this repo+folder" — presupposing a build already happened via a tool that didn't exist. `research-agent-consumption.md` §3.1 says this out loud: resolving *which* `graph_id` to pass "is a separate concern this document deliberately does not design... a future `graph_status`/`graph_build` [tool] that none of the five prior documents specified either." No document ever closed that gap, and none of the ten child-ticket seeds was "wire initial graph construction." Concretely, for the first time any user or agent touches a given repo+folder, nothing in the design produced a queryable graph — "how long until a user sees a first useful graph" had no answer other than "undefined, possibly never." **Fixed here as an explicit lifecycle decision**, choosing among the reviewer's own three suggested options rather than adopting all of them: **(c) lazy-triggered on first reference, combined with (b) an explicit UI action** — **not (a) auto-triggered on Resource registration**, which is explicitly rejected (see Rejected below). A new tool, **`graph_status(workspace_id, resource_id, folder_path)`** — read-only, `'caller'` tier, scoped by the `(resource_id, folder_path)` pair rather than a pre-existing `graph_id` — resolves the `OntologyGraph` row for that triple, **auto-provisioning one and kicking off Tier 1/1.5 extraction as an async background job** the first time it's called for a never-seen pair, and returns `{graph_id, status, indexed_at, commit, progress}` with `status ∈ {building, ready, stale, error}`. Every other `graph_` tool's `graph_id` parameter documentation is updated to say "obtained from `graph_status`," and each accepts `(resource_id, folder_path)` as an alternate input that internally resolves through the same shared provisioning helper `graph_status` exposes explicitly — so an agent starting completely fresh never needs a `graph_id` it has no way to obtain; it gets a "building, retry shortly" response on its very first call instead of a dead end. On the human side, the same provisioning helper backs an explicit "Build Graph"/"Refresh Graph" action on `OntologyGraphPage` (ticket #7, axis 5), which is where the freshness badge already lives.

- **Wave 1 (ship first, same PR):** `graph_status` (lifecycle, above), `graph_find_symbol` (name/fuzzy/qualified-name resolution — the mandatory entry point every other graph tool requires a resolved node for; returns a ranked match list plus, on a unique high-confidence match, a `detail` object with pre-filled `suggested_next_calls` into the fixed traversal tools) and `graph_module_summary` (a compact rollup of one Directory/Module/File's top-N symbols by centrality, aggregated — never per-edge — dependency/dependent counts, and freshness/provenance, directly mirroring AWB's already-shipped `get_board_summary` convention).
- **Wave 2 (ship second, gated):** `graph_search_symbols` (natural-language/semantic lookup over graph nodes, mirroring `search_resources`'s vector-with-lexical-fallback shape), gated behind the same `embeddingService.isEnabled()` check `search_resources` already uses — so it degrades gracefully rather than blocking on embedding infrastructure.
- **Deferred to backlog:** `graph_hotspots` (trivial to build — an indexed `ORDER BY pagerank DESC` — but no source in the evidence base measured it as improving task completion; a human-exploration/semantic-zoom aid, not a validated agent-accuracy lever).

Every response, from every tool, is **mandatory-bound** by three non-negotiable contracts: (1) every symbol/match carries `path`/`start_line`/`end_line` so the agent can verify by reading source; (2) every symbol/match carries `{source, confidence, indexed_at, commit}` plus an ordinal `confidence_bucket` (never a bare float); and (3) **every response from `graph_blast_radius`/`graph_neighbors` carries `completeness` (new in this revision)** — reusing the SPDX-derived `complete | incomplete | no_assertion` vocabulary axis 2 already schemas — so "zero results" and "zero results, known-incomplete coverage" (e.g. a target reached only via reflection/DI the extractor doesn't index without the optional `DECORATES` ruleset, axis 1) are distinguishable rather than both silently reading as "confirmed nothing calls this." Default row counts are 20–50, hard ceiling well under Anthropic's 25,000-token Claude Code default. All `graph_id`-scoped tools are `workspace_id`-then-`graph_id`-(or-`resource_id`+`folder_path`-)scoped as their first parameters, are read-only, and are registered at the **`'caller'` authorization tier** (any resolvable MCP identity — not `'full'`), with an explicit per-handler workspace-boundary check.

**A default confidence floor is now pinned into this Decision text for the three FIXED traversal tools too, not just the two newest lookup tools (review finding, integrity/critical).** A prior revision's MCP contract claimed `{source, confidence, indexed_at, commit}` plus `confidence_bucket` as "the safeguard against misleading edges" and treated `research-agent-consumption.md` §5 as binding — but the concrete `confidence_min: z.number()...default(0.75)` Zod default was wired only into `graph_find_symbol` and `graph_search_symbols`, never into `graph_neighbors`/`graph_blast_radius`/`graph_call_path` — the three tools that actually walk `CALLS`/`REFERENCES` edges, and the ones where a wrong edge does the most damage (e.g. "what breaks if I change X"). `research-storage.md`'s own illustrative SQL for the bounded-BFS "reach" query filtered only on `r.depth < :max_depth`, the `graph_id`, and a cycle guard — no confidence predicate; the `graph_call_path` BFS filtered only on frontier/visited sets. By default, a fuzzy-matched edge at `confidence=0.35` was traversed and returned with the same weight as a SCIP-verified `confidence=1.0` edge, distinguished only by a field value the agent had to notice and threshold itself. **Fixed here**: `confidence_min` (default `0.75`, overridable to `0` for an agent that explicitly wants speculative edges) is now a first-class parameter on **all six** graph-lookup/traversal tools, and the SQL predicate (`AND e.confidence >= :confidence_min`) is added to both the bounded recursive CTE and the BFS frontier query (axis 3). **`graph_call_path` additionally computes and returns a labelled path-level confidence rollup** (`path_confidence`, min-along-path) — `research-ontology.md` §6.5 explicitly requires "never multiply confidences along a path without recording that you did," and a prior revision never computed any path-level confidence at all, meaning a multi-hop path that only existed because of one 0.35-confidence hop was reported with no path-level honesty signal whatsoever.

**Graph tool-call recurrence is now logged from wave 1, not left unmeasured (review finding, adoption/major — closes two findings at once).** `research-prior-art.md` §6 pitfall #8 — "measure re-opens and repeat MCP calls, not first-opens" — is, per this document's own preamble, one of the pitfalls its scope fence is supposed to be shaped by, but a prior revision's §10/§11 contained zero telemetry, instrumentation, or metrics-collection commitment anywhere — the one pitfall named and then never operationalized. **Fixed here**: a Done-when line on child ticket #6 (MCP tools) requires per-agent/per-ticket call-count logging for every `graph_` tool, plus (reusing the same logging path) a comparison count of native `Grep`/`Read`/`Bash` tool calls per ticket on the same sample — giving both (a) the recurrence signal axis 5 now gates ticket #8 on, and (b) the AWB-specific dogfood evidence the next paragraph requires before treating axis 6's own tool list as settled. A human graph-view re-open count (per workspace, per week) is the equivalent Done-when on ticket #7/#8.

**This axis's adoption of `research-agent-consumption.md` §5 is now explicitly provisional, and the actual free baseline is now named (review finding, adoption/major, folds in a second adoption/major finding on the same paragraph).** A prior revision stated axis 6 "adopts its §5 'Decisive recommendation' as the binding project decision, not merely a suggestion to weigh." Every number backing "why an agent would reach for these over grep/Read" — CodexGraph's 3.11%→22.96% Pass@1 gap, `codegraph`'s self-reported 88% fewer tool calls, "Code Isn't Memory"'s p=0.003 within-harness / p=0.087 cross-harness result — comes from third-party academic benchmarks run by other agents inside other projects' harnesses, not AWB's own MCP-connected agents or AWB's own ticket workload; "Code Isn't Memory" itself found the graph's edge over a "well-built agentic-grep baseline" (OpenCode) was *not* statistically significant on the full mixed workload (p=0.087), and OpenCode's baseline is a constrained retrieval API, not the full untethered shell access AWB's own agents already have. **AWB's actual free baseline was also never named**: direct inspection confirms `fs-browser` (`apps/server/src/modules/agents/fs-browser.controller.ts`) is REST-only, gated behind `BROWSE_AGENT_FS`, with zero code-symbol awareness — correctly never proposed as the comparison — and `search_resources` searches a different corpus (the `Resource` entity, not code symbols) — also correctly kept separate (§6 trap #4). But that left the actually-relevant baseline unstated: **AWB's own agents, per this repo's own architecture (per-ticket git worktrees, full CLI harness), already have native `Grep`/`Read`/`Bash`/`ast-grep` access directly against a live, zero-staleness checkout** — no MCP tool today even wraps `git-repo-cache.ts`'s `listTree`/`getFileContent` for agent use (confirmed: `grep -rn 'listTree|getFileContent' apps/server/src/modules/mcp/tools/*.ts` returns nothing) — a stronger, zero-persistence, zero-LLM baseline than the constrained "agentic-grep" harnesses the cited academic benchmarks measured against, and precisely the baseline `research-prior-art.md` §6 pitfall #6 says every tier above Tier 1 must earn its keep against. **Fixed here**: the language is downgraded from "binding" to **provisional — the v1 working design, revisit once the wave-1 recurrence telemetry above provides AWB-specific evidence** — and the stated comparison baseline for "does this tool surface earn its keep" is now explicitly native `Grep`/`Read`/`Bash` in a live worktree, not `fs-browser` or `search_resources`, reusing the same telemetry mechanism as the recurrence measurement above rather than inventing a second measurement ticket.

### Why

This axis is newly researched in `research-agent-consumption.md`; its findings are treated here as the v1 working design (see the provisional-language downgrade above), not a re-litigation target. The evidence for *why a graph tool surface is worth building at all* is real but two-sided (§0, §1.6): five independent sources — LocAgent, RepoGraph, CodexGraph, Codebase-Memory, and "Code Isn't Memory" — converge on structural retrieval reliably winning on *efficiency* (Codebase-Memory: ~10× fewer tokens, 2.1× fewer tool calls than file exploration; a consolidated code-graph MCP tool independently measured 88% fewer tool calls) and on *localization precision* for ambiguous/indirect names (CodexGraph: BM25 collapses to 3.11% Pass@1 versus 22.96% for structural retrieval on SWE-bench-Lite), while its win on *end-to-end resolve rate* is real but smaller and benchmark-dependent — "Code Isn't Memory"'s statistically rigorous ablation found a genuine +8.5-point gain concentrated almost entirely in multi-file changes (91.3% vs. 44.9% in the ≥3-file bucket) but *not* statistically significant against a strong grep-based baseline on the full mixed workload (p=0.087), and Codebase-Memory's own honest finding is that graph-only exploration scored **lower** answer quality (83%) than file exploration (92%), just far cheaper. This is precisely why `path:line` grounding is a non-negotiable contract rather than an optional field (§1.5, §6 trap #2) — it is the specific, evidence-grounded fix for the one documented failure mode, and it is also exactly why this revision treats the overall recommendation as provisional pending AWB-specific data rather than settled: the evidence is real, but it was never AWB's own evidence, a gap this revision names rather than glosses over.

The *specific tool list* is decided by §2's survey of every production MCP code-graph server surveyed: `find_symbol` (or an exact synonym) appears in *every single one* (Serena, Polycodegraph, `code-graph-mcp`), which is "strong, independent validation that this is not a bikeshed-able naming choice." `graph_module_summary` is justified by direct analogy to AWB's own already-proven `get_board_summary` pattern (§3.3). `graph_status`'s lifecycle role is newly justified in this revision directly by `research-agent-consumption.md` §3.1's own flagged gap, closed here rather than left open. The wave sequencing and the deferral of `graph_hotspots` follow §5's own reasoning: ship the tools every surveyed system needs before anything else is useful (now including the one that makes a `graph_id` obtainable at all), gate the one tool whose value is conditional on infrastructure that may not be populated yet, and defer the one tool with no accuracy evidence behind it until usage data justifies it — usage data this revision now commits to actually collecting. The narrow-vs-fat-tool question (§3.6) is resolved by Anthropic's own tool-design guidance — "choosing the right tools to implement" over maximizing tool count — landing AWB in the middle between Polycodegraph's 18 narrow tools and `codegraph`'s single fat tool, on the principle that **response richness**, not tool count, is the actual lever (`codegraph`'s own explanation for its efficiency win: "everything... already arrives inline"). `research-ontology.md` §6.5's "never multiply confidences along a path" rule and `research-extraction.md` trap #4's default-floor mandate are the direct sources for extending `confidence_min` and the path-confidence rollup to the fixed three tools in this revision — both were already-adopted principles that a prior revision simply failed to wire into the tools where they mattered most.

### Rejected

- **A single fat "do everything" graph tool** (the `codegraph`-style consolidation) — out of scope by prior decision, since the three fixed traversal tools are already separately named and specified by `research-storage.md`; full consolidation would mean re-litigating that decision, not extending it (§3.6).
- **A large, fully granular tool family** (Polycodegraph's 18-tool shape) — rejected against Anthropic's own explicit guidance that tool-menu growth degrades agent tool-choice quality; AWB's 6–7 total `graph_`-namespaced tools is the deliberate middle path (§3.6).
- **A free-form, agent-writable query interface** (CodexGraph's write-then-translate live Cypher shape) — directly conflicts with `research-storage.md`'s own mandate that no graph traversal is ever exposed as free-form SQL/query language; every AWB tool has a fixed, bounded input schema instead.
- **Marketing "graph beats grep" as a blanket claim** in tool descriptions — the EvoCodeBench near-null result (CodexGraph 11.87% vs. no-retrieval 11.79%) and the non-significant cross-harness comparison (p=0.087) are real and specifically not to be smoothed over; tool descriptions state precisely *when* a tool helps (ambiguous names, multi-file changes), never universal superiority (§6 trap #1).
- **Dropping `path:line` or provenance fields to save tokens** — explicitly identified as "a regression, not a feature": Codebase-Memory's 83%-vs-92% quality gap is directly attributable to a graph-only agent not grounding back to source (§6 trap #2).
- **Merging `graph_search_symbols` into `search_resources`** — they search different corpora (graph symbol nodes vs. the `Resource` entity) and must stay separate tools despite sharing conventions, to preserve the `Resource`/`OntologyGraph` scope boundary (§6 trap #4).
- **A seventh, standalone "Graph lifecycle" axis** — the underlying gap (review finding, adoption/critical, above) is real and is fixed, but as a subsection of axis 6, not a new axis, per this document's own explicit 6-axis structure; `graph_status` is the concrete tool, not a new axis of decision-making.
- **Auto-triggering graph construction on Resource registration or first commit push** (one of three lifecycle options the review raised) — rejected: unconditionally paying Tier 1/1.5 extraction cost for every registered Resource, whether or not its graph is ever queried, is exactly the "ship unconditionally before demonstrated value" pattern this design already rejects elsewhere (§10a item 1; `research-prior-art.md` §6 pitfall #6). Lazy provisioning on first reference (adopted) ties cost to actual demonstrated use instead.
- **Keeping the "binding" framing for `research-agent-consumption.md` §5** without AWB-specific evidence — rejected in this revision; downgraded to provisional (see Decision above), pending the wave-1 telemetry this revision commits to collecting.

### Integration points

- **`apps/server/src/modules/mcp/tools/index.ts:42-65`**'s `discoverToolModules()` auto-globs `*-tools.{ts,js}` and resolves `register[A-Z].*Tools` exports — a new `apps/server/src/modules/mcp/tools/ontology-tools.ts` needs **zero** edits to `registerAllTools()` itself; `resource-tools.ts:20-298` is the closest existing template for the `dataSource`/`logger`/`embeddingService`-destructuring, `ok()`/`err()`-helper, zod-schema shape (`scout-server.md` §6a). **On the sql.js backend, `ontology-tools.ts` must be wired to the ontology DataSource (axis 3), not the default-injected primary one.**

## 10. What we are NOT building in v1

Scope discipline matters here specifically because this is a research/design epic — implementation happens entirely in child tickets, and every item below is a fence against a child ticket silently expanding past what this document actually decided.

### 10a. Deferred (sequenced later, not architecturally excluded)

1. **SCIP ingestion and LSP-on-demand (Tier 2/2b)** — designed (axis 1) but not built until Tier 1/1.5 alone are shipped and shown to carry real value, per Aider's own validated-floor lesson (`research-prior-art.md` §4.3, pitfall #6: "treat every tier above Tier 1 as needing to beat a zero-persistence, zero-LLM baseline before it ships as anything other than optional").
2. **LLM enrichment (Tier 3) as anything but strictly optional** — the semantic/`curated` layers must never be the argument for why the structural graph is worth building; CodeSee's own founder's post-mortem is direct evidence an AI layer does not rescue a structural product nobody was already using (`research-prior-art.md` §3.3, pitfall #3).
3. **The sigma.js rendering engine build (child ticket #8), specifically — revised in this document's v1.1 review response.** Route/chrome/freshness-badge (ticket #7) ships in wave 1; the actual canvas build is gated behind the wave-1 MCP-tool recurrence signal (axis 5/6) — see item 12 below. This replaces a prior, internally-inconsistent framing ("real work, not deferred... but not the feature's adoption bet") that scheduled the engine build unconditionally while gating every other speculative-value feature in this list. The graph's first-class surface in v1 remains the MCP tool calls agents already make mid-task (`research-prior-art.md` §2.4, §6 pitfall #1); the human-browsable UI is real, committed work, just sequenced behind evidence like everything else here.
4. **cosmos.gl raw/expanded rendering mode** — the sigma.js aggregated view ships first (once ungated per item 3); the GPU-simulated opt-in mode is a follow-on once users demonstrably hit the aggregated view's ceiling.
5. **`graph_search_symbols` and `graph_hotspots` MCP tools** — waved and deferred per axis 6's decision; not part of the first PR.
6. **DuckDB analytics sidecar** — a real, correctly-scoped addition (axis 3) but not a day-one requirement; ships once the primary relational store and query layer are live and a genuine OLAP need is felt.
7. **RDF/JSON-LD export** (N3.js/jsonld.js) — a designed export capability with no consumer yet; build when something (an external tool, a compliance requirement) actually needs to read the graph as RDF.
8. **pgvector HNSW acceleration** — gated behind measured embedding volume; brute-force cosine similarity is the v1 default on both backends.
9. **Workspace-profile custom node/edge types** — the extensibility *mechanism* is schema'd (axis 2, §9 of `research-ontology.md`), but no UI/API exists yet for a workspace to actually define one; core profile only in v1.
10. **GPU-accelerated Leiden (cuGraph-class)** — CPU `graphology-communities-leiden` only; GPU is a documented scale-up path for when AWB's own measured graphs approach the range that needs it, not a v1 dependency.
11. **Auto-population of `AFFECTS_CODE`/`ABOUT` ticket-bridge edges at scale** — the edge *types* are schema'd as a differentiator (axis 2), but wiring automatic population from ticket activity into the graph is future work, not this epic's build scope.
12. **Moving the sql.js flush off the main thread, and per-workspace/per-graph sql.js files** (axis 3, new in this revision) — real follow-up paths if the dual-DataSource-plus-row-ceiling mitigation proves insufficient once actually benchmarked; not v1 commitments.
13. **A minimal NestJS-aware `@ast-grep/napi` ruleset for reflection/decorator-driven dispatch** (axis 1, new in this revision) — its *scope* is now pinned (guards/interceptors/pipes/`@Cron()`/`@EventPattern()`), but it remains optional and non-blocking; queryability never depends on it shipping in the first PR.

### 10b. Permanently out of scope (architectural exclusions — revisiting these requires a new design doc, not a follow-on ticket)

1. **Any graph database other than SQLite/Postgres** (Kuzu, Neo4j, or otherwise) — rejected in axis 3 on maintenance/archival and operational-fit grounds that don't change with more engineering time.
2. **Unbounded recursive CTEs and full transitive-closure precomputation** — not a v1 corner cut; the row-explosion/OOM failure mode (axis 3) is a property of the SQL standard's recursive-CTE semantics, not an implementation gap AWB will close later. `graph_call_path` is application-orchestrated BFS forever, not "until we have time to do it properly."
3. **A free-form, agent-writable graph query language** (Cypher-equivalent or otherwise) — every MCP tool has a fixed, bounded schema by design (axis 6); this is a trust/safety boundary, not a v1 limitation.
4. **Joern/CPG-grade dataflow or taint analysis** — explicitly named in `research-extraction.md` §2.8 as "the right answer if AWB ever wants" this, and just as explicitly kept out of the ontology graph's own scope; if ever built, it is a separate, optional deep-analysis plugin attaching `derived`-layer edges, not a rearchitecture of this design.
5. **OWL-DL reasoning over the graph** — the two-namespace LPG/SKOS split (axis 2) is chosen specifically because AWB's useful inferences are graph traversals, not description-logic entailments; adding a reasoner would be solving a problem this design doesn't have.
6. **Auto-triggering graph construction unconditionally on Resource registration** (axis 6, new in this revision) — one of the graph-lifecycle options explicitly considered and rejected; lazy, on-demand provisioning is the permanent v1+ mechanism, not a stopgap pending a "better" always-on trigger.
