# Incremental Update at Scale — Deep Technology Research (for AWB Ontology Graph)

Date: 2026-08-21/22. Target: keeping a per-workspace Ontology Graph fresh as a repo grows to millions of LOC, without re-extracting everything on every commit and without a full recompute on every keystroke. This document assumes and builds on the two prior research documents in this folder — `research-extraction.md` (tree-sitter-tags mandatory tier, SCIP optional tier, LLM-bounded enrichment tier, the measured AWB density of 27.6 definitions/kLOC and 243.6 references/kLOC) and `research-ontology.md` (LPG-in-SQLite storage, the `layer`/`confidence`/`symbol_id`/bitemporal schema, and the six-step freshness algorithm sketched in its §8.6) — and does **not** re-argue those conclusions. It goes one level deeper on exactly one question: *how do production systems that face this same problem actually bound the cost of an incremental update, and what does that mean concretely for AWB's schema and scheduler?*

**Bottom line up front:** every production system that has solved "keep a derived graph fresh under continuous small edits" — rust-analyzer/salsa, TypeScript's `tsserver`, GitHub's CodeQL, Meta's Glean, and the whole Bazel/Buck2/Turborepo/Nx build-cache family — converges on the same four mechanisms, in the same order of load-bearing importance:

1. **Content-addressed, stable identity** for every unit of work (a file, a symbol, a build action) so "did this change" is a hash comparison, not a structural diff or a sequential counter.
2. A **reverse-dependency index** so invalidation walks *forward from the change* to its consumers, instead of a query walking backward through everything it might depend on.
3. **Early cutoff** — stop propagating a change the instant a re-verified node's output is provably identical to before, even though its inputs technically changed underneath it.
4. **Tiered durability / priority** — expensive, rarely-changing things (stdlib, vendored dependencies, LLM-generated summaries) are checked and re-derived far less often than cheap, frequently-changing things (the file currently being edited).

AWB's design already has (1) — `symbol_id`, SCIP-shaped, version-stripped — and a version of (3) — soft-edge staleness by evidence-hash mismatch. What is missing, and what this document supplies concretely, is (2), an explicit reverse-reference index and the two-phase mark→verify algorithm that walks it, and (4), a durability/priority scheduler for the LLM tier backed by Anthropic's actual batching and caching primitives. Sections 1–5 below answer the five research questions in order; §6 turns them into a concrete architecture recommendation; §7 lists traps.

## 1. What production incremental analyzers actually do (git-diff-based reindexing)

### 1.1 rust-analyzer + salsa: revisions, dependency graphs, and one hard invariant

rust-analyzer's incremental core is the `salsa` crate, "a generic framework for on-demand, incrementalized computation… inspired by adapton, glimmer, and rustc's query system" (https://github.com/salsa-rs/salsa). The model: a `Database` holds `input`s (ground truth the IDE feeds in — file text, the crate graph) and `tracked function`s (pure, memoized derivations). Every time an input is set, salsa bumps a global **revision** counter; that is the *entire* cost of a keystroke — "whenever an input changes, Salsa does only two things (so, O(1)): change the input, increment the global version" (https://salsa-rs.github.io/salsa/overview.html). No invalidation happens at write time.

Invalidation happens lazily, at *read* time, via the **red-green algorithm** (the origin of the name "salsa"). When a tracked function runs, salsa records which other tracked functions and inputs it read, and the revision at which each one last actually changed. On the next read, salsa walks that recorded dependency list: if every dependency is still "green" (unchanged since it was last verified), the cached result is reused with no recomputation at all; if a dependency might have changed, salsa re-verifies it recursively — and only re-runs the function's own body if a *real* dependency changed (https://salsa-rs.github.io/salsa/reference/algorithm.html). Crucially, salsa supports **early cutoff** (also called *backdating*): if a dependency's revision moved but its recomputed value is byte-identical to the previous one — the canonical example is a whitespace edit that doesn't change the parsed AST — salsa "backdates" the result, i.e., records that the *value* didn't change even though the *input* did, and nothing downstream re-executes (https://salsa-rs.github.io/salsa/reference/algorithm.html).

That alone is not enough at IDE scale. rust-analyzer's own postmortem is blunt about the residual cost: "any change to `src/lib.rs` necessitates checking all the queries related to standard library (which adds up to about 300ms)" — because in a pure red-green scheme, *every* downstream query still has to be walked and re-verified, even if none of them actually change (https://rust-analyzer.github.io/blog/2023/07/24/durable-incrementality.html). The fix, **durability**, upgrades the single global revision counter into a small version *vector* with tiers ("volatile, normal, durable" in the post's own words); an input's durability is set once (stdlib = durable, workspace files = volatile), derived queries inherit the *minimum* durability of their inputs, and when only a volatile input changes, salsa can skip validating every query whose durability floor is higher, without walking the dependency graph at all (https://rust-analyzer.github.io/blog/2023/07/24/durable-incrementality.html). This is the load-bearing insight for §6 below: durability is not the same mechanism as the dependency graph — it is a cheap, coarse pre-filter that avoids ever *entering* the graph walk for the (large) part of the codebase that essentially never changes.

Finally, rust-analyzer's architecture doc states the actual product-level invariant this machinery exists to deliver: **"typing inside a function's body never invalidates global derived data"** (https://rust-analyzer.github.io/book/contributing/architecture.html). The mechanism behind that sentence is `ItemTree` — "a stable summary of a syntax tree" that captures a file's declarations (signatures) but is structurally decoupled from function bodies, so editing a body can never even *produce* a dependency edge into the signature graph in the first place (https://rust-analyzer.github.io/book/contributing/architecture.html). This is precisely the `signature_hash` vs. `file_content_hash` split recommended in §6.

### 1.2 TypeScript's `tsserver` / `tsc --build`: per-file signatures in `.tsbuildinfo`

TypeScript's `--incremental` flag (and `--build` for project references) "saves information about the project graph from the last compilation" to a `.tsbuildinfo` file next to the output; on the next invocation the compiler reads it back and uses it to "detect the least costly way to type-check and emit changes" (https://www.typescriptlang.org/tsconfig/incremental.html, https://www.typescriptlang.org/docs/handbook/release-notes/typescript-3-4.html). The file is explicitly not part of the runtime artifact and is safe to delete — it exists purely as a persisted **verifying trace** (§4.1) so a second `tsc` invocation doesn't have to re-derive dependency information from scratch. Composite projects (project references) always produce one, which is what lets a monorepo build only the packages whose declaration output actually changed, cascading to dependents only when a `.d.ts` shape changes — the TypeScript analogue of early cutoff at the package boundary. Separately, `tsserver`'s `ProjectService` — the component VS Code talks to — deliberately runs "background parsing of open files and background compilation of projects with open files… for improved responsiveness," i.e. it prioritizes the files the user actually has open over the rest of the project graph, which is direct precedent for the priority-queue design in §5.2 (search-derived, corroborated by TypeScript's public issue tracker discussion of `ProjectService` behavior).

### 1.3 CodeQL: the single most useful incremental-extraction case study

GitHub's Tamás Szabó published "Incrementalizing Production CodeQL Analyses" (ESEC/FSE 2023, https://arxiv.org/abs/2308.09660), and it is the closest existing analogue to AWB's own extraction pipeline: source → extractor emits "trap files" → importer builds a relational **EDB** (extensional database) → the QL compiler/solver computes an **IDB** (intensional database, the analysis result) via semi-naive Datalog evaluation. This is structurally identical to AWB's tree-sitter-facts → resolved-edges → derived-graph pipeline.

The paper's headline finding is a trap AWB must avoid by construction. On a real production codebase ("spree," ~73 kLoC Ruby, EDB averaging 2.76 million tuples, IDB averaging 217.41 million tuples), the authors found that **the average impact of a commit on the EDB was ~4 million tuples — larger than the EDB itself — irrespective of how small the actual code change was.** The root cause: "the trap importer rolls out ids sequentially based on a counter, so a small change to one file may end up shifting ids for all the AST nodes later in the file *and all subsequently imported files*." An unstable identity scheme silently converts every local edit into a global rewrite. Their fix — construct a stable global key for every AST node "based on paths in the AST," hash that path-based key instead of using a counter, and separately reuse ADT-instance id assignments across commits by persisting the id pool to disk — reduced the change rate (fraction of the database that actually differs) to "at or below 5%" for commits touching up to 1000 lines, and made the impact "proportional to the size of the code change" instead of constant-and-huge (https://arxiv.org/abs/2308.09660). This is the single strongest piece of evidence in this whole document for why AWB's `symbol_id` must be content/path-derived and never a counter: it is not a style preference, it is the precondition for incrementality existing at all.

The same paper is equally useful as a cost-of-full-incrementality cautionary tale (see §7). Beyond the research paper, incremental analysis has since shipped in production CodeQL: the `--overlay-base` flag builds a base database on the default branch that caches intermediate query results; PR analysis records `git ls-files --recurse-submodules --format='%(objectname)_%(path)'` — i.e., **git object IDs, not a custom hash**, reused directly as the change-detection key — diffs that OID map against the base snapshot to get exactly the changed/added/deleted files, and re-extracts only those into an "overlay" on top of the cached base (https://docs.github.com/en/code-security/how-tos/find-and-fix-code-vulnerabilities/scan-from-the-command-line/incremental-analysis). It is currently scoped to `build-mode: none` languages and has version floors per language (Java/JS/Python/Ruby ≥2.23.8-9, C/C++ ≥2.25.0, C# ≥2.24.1, Go ≥2.24.2) (https://docs.github.com/en/code-security/how-tos/find-and-fix-code-vulnerabilities/scan-from-the-command-line/incremental-analysis), and continues to expand — Go, C/C++, and CLI support for third-party CI landed as recently as June 2026 (https://github.blog/changelog/2026-06-10-incremental-analysis-for-go-c-c-and-codeql-cli/, https://github.blog/changelog/2026-03-24-faster-incremental-analysis-with-codeql-in-pull-requests/, https://githubnext.com/projects/incremental-codeql/). The direct lesson for AWB: **git's own object identity is a free, already-computed content hash** — AWB's `git diff --name-status` step (already decided in `research-ontology.md` §8.6.1) should key off git OIDs, not re-hash file bytes itself, wherever git is the source of truth.

### 1.4 Meta Glean: immutable layers and ownership-scoped incrementality

Glean's incrementality model is structurally the most different from the other three, and instructive because of it. Rather than mutating a database, Glean builds new increments as separate immutable "stacked" databases on top of a base (https://glean.software/docs/implementation/incrementality/). The mechanism that makes a stacked DB *cheap* rather than a full duplicate is **ownership**: an arbitrary string-named "unit" owns a set of facts; ownership sets compose via logical `||` (disjunction) and `&&` (conjunction) into a `UsetId`, and building an incremental DB is a matter of computing a *slice* — the visible subset of `UsetId`s — rather than re-deriving facts (https://glean.software/docs/implementation/incrementality/). Ownership propagates automatically through references: if fact `F` references fact `B` owned by unit `A`, `F`'s owner becomes `A || B`, which "ensures no dangling references" ever have to be checked for at query time (https://glean.software/docs/implementation/incrementality/). Derived facts follow the dual rule — a fact derived from sources with owners `O1..On` is visible **iff all of `O1..On` are visible**, i.e., conjunction — and this propagation step runs "after all the facts are written, but before derivation starts" (https://glean.software/docs/implementation/incrementality/), turning "is this derived fact still valid" into a single bounded pass over the *actually-changed* ownership sets rather than a query-time join over the whole database. This is a different flavor of the same idea as rust-analyzer's durability tiers and CodeQL's overlay bases: **partition the world so that "did anything relevant change" can be answered without touching the unaffected partition at all.**

### 1.5 The common shape

Across all four systems the pattern is identical in outline, differing only in mechanism: (a) give every unit of derived work a **stable identity** independent of build/extraction order; (b) record, per unit, **what it actually depended on** the last time it was computed; (c) on a new build, compare *only the changed inputs'* stable identities against that record to find the frontier of possibly-affected units; (d) **stop walking outward** the moment a re-verified unit's output is unchanged. Sections 3 and 4 below turn (b)–(d) into an algorithm AWB can implement directly on top of its existing `symbol_id`/`layer`/bitemporal schema.

## 2. Merkle trees and content-hash caches: the build-cache literature

### 2.1 The unifying theory: Build Systems à la Carte's trace taxonomy

Mokhov, Mitchell, and Peyton Jones's "Build Systems à la Carte" (ICFP/PACMPL 2018, https://www.microsoft.com/en-us/research/wp-content/uploads/2018/03/build-systems-final.pdf) is the paper that turns "Make vs. Bazel vs. Nx" from folklore into a small, precise design space, and it is the best available vocabulary for AWB's own design. It defines **minimality** formally: "a build system is minimal if it executes tasks at most once per build, and only if they transitively depend on inputs that changed since the previous build" (Definition 2.1) — this is the property AWB's freshness pipeline is trying to have. It then separates every build system into two orthogonal choices: a **scheduler** (the order tasks run in — *topological*, computed once from statically-known dependencies; *restarting*, build in an arbitrary order and abort-and-restart a task when a just-discovered dependency turns out to be stale, which is literally what Bazel and Excel's calc-chain do; or *suspending*, start a task and pause it mid-flight when it requests a not-yet-built dependency, resuming once that dependency is ready, which is what Shake does) and a **rebuilder** (how a single key decides whether it needs rebuilding).

The rebuilder taxonomy is the part most directly reusable by AWB:
- **Dirty bit** — one bit per key, set dirty when *any* transitive dependency changes, cleared on rebuild. This is Make's mtime comparison, over-approximating: Excel, lacking full dependency information, marks a cell dirty "if the formula statically refers to a dirty cell, or… uses a function like `INDIRECT` whose dependencies cannot be guessed" — i.e., it is *forced* to over-invalidate when it can't prove safety, which is the anti-pattern AWB must avoid for its own dynamic-language, DI-container, and monkey-patch cases (already flagged as trap #4 in `research-extraction.md`).
- **Verifying trace (VT)** — instead of a bit, persist the *hash* of the key's own value plus the hashes of the values its dependencies had at that time; "the verifying trace store only small hashes, so it is helpful for it to be of modest size." Rebuilding is answered by `verifyVT`: recompute the current hashes and compare. This is what salsa's fingerprints, rustc's `DefPathHash`+`Fingerprint`, and TypeScript's `.tsbuildinfo` signatures all are.
- **Constructive trace (CT)** — a VT that additionally stores the *actual resulting value*, keyed by the hash of its dependencies, so that a key with matching dependency hashes can be satisfied *without doing any work* — "since we are storing the complete result… it makes sense to record many constructive traces per key, and to share them with other users, providing cloud-build functionality." This is exactly Bazel's/Buck2's remote cache: a content-addressed action → output map, sharable across machines.
- **Deep constructive trace (DCT)** — a CT that skips intermediate levels entirely and hashes only the *terminal input keys* (the paper frames this as parametrized by how many dependency levels `n` you skip; `n=1` is an ordinary CT, `n=∞` means you hash straight through to the leaves). This is exactly what Turborepo and Nx do (§2.3): one hash over the transitive closure of source files, no intermediate per-file trace chain. The paper's caveat is the one AWB must respect: **"deep constructive traces require the tasks to be deterministic, as otherwise it is possible to violate correctness,"** and they "cannot support early cutoff, other than at `n` levels of dependencies" — meaning a DCT-style single flat hash is *wrong* to use for anything whose output is non-deterministic (an LLM call) or for anything you want fine-grained early cutoff on (a single symbol's signature inside a large file).

The paper instantiates this framework against Make, Excel, Shake, Bazel, CloudBuild, Buck, and Nix and shows they are all points in the same two-axis space (scheduler × rebuilder) — which is a strong signal that AWB's three-tier pipeline should pick its scheduler/rebuilder combination *deliberately* rather than by accretion. §6 makes that choice explicit.

### 2.2 Bazel / Buck2: content-addressed action graphs in practice

Bazel's build graph literally *is* a Merkle tree: "files are leaf nodes digested using their content [and] directories are tree nodes digested using digests from their subdirectories and children files," using SHA-256 by default; the **action cache** maps a digest of "the command line, inputs, environment, and other execution metadata" to cached result metadata, and the **content-addressable store (CAS)** holds outputs by hash, with remote execution uploading inputs "as a Merkle tree of directories and file digests" so that "shared subtrees, such as toolchains and external repositories, can be reused without re-uploading the same blobs" (https://bazel.build/remote/caching). This is a real-world constructive trace at scale, and the "shared subtrees reused without re-upload" property is exactly the free win AWB can copy for its Tier-1 tree-sitter facts (§6.3).

Buck2's incremental engine, **DICE**, is explicitly genealogically related to the systems above — its own docs state DICE "is a dynamic incremental computation engine that supports parallel computation, inspired by Adapton and Salsa" (https://github.com/facebook/buck2/blob/main/dice/dice/docs/index.md) — and its own incrementality doc gives the cleanest one-sentence statement of the goal this whole document is chasing: **"DICE tracks the reverse dependencies (rdeps) of computations to achieve O(invalidated subset) traversals and O(changed subset) recomputations for a given request"** (https://github.com/facebook/buck2/blob/main/dice/dice/docs/incrementality.md). Per-action, Buck2 computes "a digest… a hash of an action's command and all its inputs" and checks the remote cache by that digest before executing (https://www.tweag.io/blog/2023-07-06-buck2/); unlike Bazel's phased target-graph/action-graph split, Buck2 uses one dynamic (monadic) graph throughout, which its docs describe as enabling finer-grained dependency tracking and fewer unnecessary rebuilds than Bazel's coarser phase boundary.

### 2.3 Turborepo / Nx: deep constructive traces at the task level

Turborepo computes a **global hash** (root config + transitively-included internal-package sources) and a **task hash** (glob-matched `inputs` files + selected env vars + internal dependency versions); "because the key is a content hash of the inputs, there is no invalidation logic to get wrong: a changed input produces a different key, and stale entries are simply never looked up again" (https://turborepo.dev/docs/crafting-your-repository/caching) — a textbook deep constructive trace, deliberately trading fine-grained early cutoff for simplicity. Nx computes a task hash from "project source files and files from project dependencies," workspace configuration, external dependency versions, OS/CPU architecture, and CLI arguments (https://nx.dev/docs/concepts/how-caching-works) — the same DCT shape — but layers a genuinely different, complementary mechanism on top for CI: `nx affected` uses git to find changed files, maps them to owning projects via the **project graph**, and then walks that graph's **reverse edges** to find every project that (transitively) depends on a changed one — "if the affected node `lib10` is used by `lib4`, which is used by `app1`, all of these nodes will be added to the affected project graph," implemented via a `reverse()` devkit function that flips every edge in the project graph (https://nx.dev/docs/features/ci-features/affected). Nx's own framing is the one to steal verbatim: **"affected calculations remove projects that don't need a task, while caching avoids rerunning matching tasks in the remaining graph… the combination provides better results than one or the other"** (https://nx.dev/docs/features/ci-features/affected). This is precisely the two-layer design AWB needs — a coarse reverse-graph walk to find the *candidate* blast radius, and a fine content-hash check within it to avoid doing any work for candidates that turn out unaffected.

## 3. Cross-file edge invalidation: reverse indices and bounded blast radius

This is where §1 and §2's mechanisms combine to answer the concrete question: *file A changes — which edges, in which other files, need to be recomputed?*

**The identity precondition (recap of §1.3).** CodeQL's own history is the cleanest demonstration that this question is *unanswerable* without stable identity: with counter-based ids, "which edges reference file A's symbols" is not even a well-defined set across commits, because every symbol in every file that happens to be parsed after A shifts identity too. Only once ids are content/path-derived does "who references symbol X" become a query that returns the same conceptual answer release over release.

**rustc's `DepGraph`: stable identity + a graph-walk algorithm.** rustc solves the "which query results survive" problem with `DefPathHash` — a 128-bit hash of a *path* (`std::collections::HashMap`, not a raw numeric `DefId`) that is stable across compilation sessions even though the numeric ids backing it are re-assigned every run (https://rustc-dev-guide.rust-lang.org/queries/incremental-compilation-in-detail.html). Every query invocation becomes a `DepNode` in a graph; edges record "which other queries or inputs went into computing this query's result." On a new compilation, `try_mark_green()` recursively walks a node's *recorded* dependency edges (from the *previous* session's graph, loaded read-only) and marks it green if every dependency is still green — reusing the prior result with **zero re-execution** — or re-runs the query and compares its new `Fingerprint` hash to the old one, again enabling early cutoff when the fingerprint hasn't moved. When a node is marked green, "the node and the edges to its dependencies" are copied straight from the old graph into the new one, so the cost of "nothing changed here" is O(1) per node, not a re-derivation (https://rustc-dev-guide.rust-lang.org/queries/incremental-compilation-in-detail.html). This is the general algorithm AWB's Tier-1.5 resolver should implement directly (concretized in §4.2 and §6.2).

**Glean's ownership propagation as a bounded fixpoint (recap of §1.4).** Because a derived fact's visibility is the conjunction of its sources' visibility, and that propagation is computed once per increment before any derivation begins, Glean never has to ask "is this derived fact stale" as an open-ended graph query — it is answered by construction, bounded to exactly the facts whose ownership sets actually changed in this layer.

**Nx / Buck2: the reverse graph, made literal.** Nx's `reverse()` project-graph flip and Buck2 DICE's `rdeps` tracking (§2.2, §2.3) are, structurally, the exact same object AWB needs: an index from "thing that was defined here" to "the (much smaller) set of things that consume it." The key design point both systems make implicitly is that this index is maintained **at the granularity that makes the reverse walk cheap** — Nx indexes at the *project* level (dozens to low-thousands of nodes), not the file or symbol level, specifically because a symbol-level reverse graph across a huge monorepo would itself be expensive to maintain. AWB's own density numbers make the equivalent granularity choice concrete: at 27.6 definitions/kLOC and 243.6 references/kLOC (`research-extraction.md` §1), a 10 MLOC repo has ~280k definitions and ~2.4M raw reference edges — a *symbol*-level reverse index at that scale is a ~2.4M-row SQLite table with a `(dst_symbol_id)` index, which is well inside SQLite's comfort zone (as already established for the forward edge table in `research-ontology.md` §8.7), but a **file**-level reverse index (which files import which other files) is smaller still (bounded by file count, not reference count) and should be the *first* hop checked before ever touching the symbol-level table — mirroring Nx's project-level-first design.

**Differential dataflow: the general, and more expensive, answer.** Frank McSherry's differential dataflow generalizes incremental view maintenance into a standing computation: "instead of asking 'what is the result of this query', it asks 'given that the input changed by this much, how does the output change'… a graph of operators sitting between the base tables and the view, permanently subscribed to change," where each operator "only need[s] to revisit previously received input records with the same keys as newly arriving inputs" (search-derived synthesis of the public differential-dataflow literature, corroborated by the CIDR 2013 "Differential Dataflow" paper, https://www.cidrdb.org/cidr2013/Papers/CIDR13_Paper111.pdf). This is the *asymptotically ideal* version of a reverse index — every derived fact is automatically, incrementally maintained by key, with no manual "walk the reverse edges" step at all. It is also a standing streaming runtime, not a batch SQLite table, and adopting it wholesale would mean AWB running a second, always-on compute engine alongside NestJS+TypeORM — a much bigger operational bet than the problem currently warrants. The right way to use this idea (see §6) is to **borrow the key-indexed delta-propagation principle**, not the runtime: model each edge-invalidation step as "given that symbol S's signature changed, which rows in the edge table have `dst_symbol_id = S`", which is a single indexed SQL query, not a graph traversal — differential dataflow's insight, implemented the boring way.

## 4. Computing the minimal recomputation set

### 4.1 Formal minimality and picking a scheduler/rebuilder pair for AWB

Using the Build Systems à la Carte vocabulary (§2.1) to be precise about what AWB should build: AWB's file-import graph is **statically known** (imports are lexically visible), so a **topological scheduler** is correct and sufficient for Tier 1 — no restart/suspend machinery is needed, because AWB never needs to discover a dependency mid-task the way Excel's `INDIRECT` or a monadic build does. Tier 1.5's cross-file resolver, however, has dependencies that are only known *after* Tier 1 runs (you don't know which files reference symbol S until S is extracted) — this is the one place a **restarting**-style two-pass approach is appropriate: extract first (assume no cross-file deps), then resolve against the now-complete symbol table, rather than trying to interleave extraction and resolution in one pass. For the rebuilder: Tier 1/1.5 should be a **verifying trace** (hash comparison against the last-known signature, §4.2) — cheap, no value sharing needed since re-parsing a changed file is already sub-millisecond-to-low-single-digit-milliseconds per file at AWB's measured 82k lines/s (`research-extraction.md` §1). Tier 2 (SCIP) and Tier 3 (LLM) outputs, by contrast, are worth sharing across identical inputs (a vendored copy of a file, a monorepo package duplicated in two workspaces) and should be **constructive traces** keyed by `(content_hash, extractor_version)` — never deep constructive traces, because SCIP indexers are not path-independent (they embed compiler configuration) and LLM output is explicitly non-deterministic (`research-extraction.md` §2.13 already flags this).

### 4.2 Early cutoff, made concrete: the signature/body split

Every system in §1 arrives at the same trick to stop a change from cascading further than it has to: separate a definition's **shape** (what other files can legally depend on) from its **implementation** (what only affects the file itself). rust-analyzer calls this `ItemTree` vs. function bodies; rustc calls it query-level fingerprint comparison; TypeScript calls it the `.d.ts`-shape signature that `--build` cascades on. AWB's schema already has the right column to carry this (`signature` on `Callable` per `research-ontology.md` §8.3) — what's missing is treating it as a **second, independently-hashed field**: `signature_hash = hash(name, kind, arity, visibility, param_types, return_type, heritage)`, distinct from the node's overall `content_hash`. The two-phase algorithm this enables:

1. **Phase A (always-on, per changed file):** re-parse the file (Tier 1). Diff its new symbol table against the old one by `symbol_id`. For every symbol whose `content_hash` changed, recompute `signature_hash`. If `signature_hash` is unchanged (a body-only edit — the overwhelmingly common case for a single keystroke or a bug fix), **stop here** — no other file's edges need touching, matching salsa's backdating and rustc's fingerprint-equality early cutoff exactly.
2. **Phase B (bounded, only for symbols whose `signature_hash` did change, or that were added/removed):** look up `reverse_edge_index(dst_symbol_id)` — a single indexed query — to get the (typically small — see §3's Nx-style file-level-first design) set of files holding an edge that targets this symbol. Re-run the Tier-1.5 resolver *only* for those files' outgoing edges, not for their own definitions (which are unaffected). This is the literal AWB instantiation of Buck2's "O(invalidated subset) traversals and O(changed subset) recomputations."
3. **Phase C (lazy, never on the write path):** any `semantic`/`derived` edge whose `evidence_ref[].content_hash` no longer matches its cited slice flips to `status='stale'` — already decided in `research-ontology.md` §8.6.4. What this document adds is the *scheduling* of re-promotion (§5).

### 4.3 Durability as a pre-filter, not a graph walk

Section 1.1's salsa durability lesson generalizes directly: AWB should tag `Repository`/`File`/`Module` nodes with a durability level derived from their provenance — `volatile` for anything under the workspace's tracked source roots, `stable` for anything resolved from a lockfile-pinned `ExternalPackage` (already a node type per `research-ontology.md` §8.3), `frozen` for anything under a vendored/generated path already flagged `is_generated`. On a commit that only touches `volatile` files, Phase B's reverse-index walk should **never be issued** against `stable`/`frozen` partitions at all — not "walked and found unaffected," but literally skipped, the same way salsa skips validating stdlib-durability queries without touching the dependency graph. This matters at scale precisely because `stable`/`frozen` code is exactly the code with the highest fan-in (§5.4) — it is disproportionately expensive to walk and disproportionately unlikely to have actually changed.

### 4.4 Demand-driven vs. eager: when *not* to compute the minimal set at all

Adapton's contribution ("Adapton: composable, demand-driven incremental computation," PLDI 2014, https://dl.acm.org/doi/abs/10.1145/2666356.2594324) is a caution against over-applying §4.1–4.3: eagerly recomputing everything a change *could* affect is wasteful if nothing is currently asking for that output. Adapton's demand-driven semantics only recomputes what an active "observer" still needs, tracked in a "demanded computation graph," rather than propagating a change to every structurally-dependent node whether or not anyone is looking at it. Buck2's DICE cites Adapton as a direct ancestor for exactly this reason (https://github.com/facebook/buck2/blob/main/dice/dice/docs/index.md). For AWB this argues for **not** eagerly re-running Phase B for `semantic`/`derived`-layer consequences of a structural change at all — mark them `stale` (cheap, Phase C) and only actually recompute a stale community summary, centrality score, or concept link when an MCP tool call or UI open event demands it. This is the same trade LazyGraphRAG makes (already the load-bearing citation in `research-ontology.md` §4.2/§10) and Adapton is the general theory behind why it's the right default, not just a cost hack.

## 5. LLM cost control under fan-out: batching, priority, and budget

### 5.1 The batching and caching primitives to build on

Two Anthropic API primitives map directly onto "amortize the LLM tier":

- **Message Batches API**: asynchronous, up to 100,000 requests or 256 MB per batch, **50% off standard per-token pricing** for both input and output, with "most batches complet[ing] within 1 hour" against a documented worst case (https://docs.claude.com/en/docs/build-with-claude/batch-processing). Since `research-extraction.md` §2.13 already establishes that LLM enrichment must never sit on AWB's write/critical path, every Tier-3 enrichment call is, by construction, a batch-API candidate — there is no reason to pay full synchronous price for work that is explicitly deferred and budgeted.
- **Prompt caching**: cache reads cost ~10% of base input price (a 90% reduction) against a 25% premium to write the cache in the first place — worthwhile once a cached prefix is reused more than roughly once (https://claude.com/blog/prompt-caching). Reported latency wins are substantial (a 100K-token "chat with a book" scenario dropped from 11.5s to 2.4s, a 79% reduction) (https://claude.com/blog/prompt-caching). This is the concrete mechanism for HCGS/Code-Craft-style bottom-up summarization (already the Tier-3 design in `research-extraction.md` §2.13): the *file's full source plus its already-computed child summaries* is exactly the kind of large, reused-across-siblings prefix prompt caching is built for — summarizing five sibling functions in the same file should share one cache write, not pay full input price five times. Note the operational catch: cache TTL defaults to a short window (reported as 5 minutes as of an early-2026 pricing change, with a 1-hour option available at a higher write premium) — this means AWB's enrichment batch windows should either (a) drain a coherent unit of work (one file's sibling functions, one folder's child summaries) within a few minutes of each other, or (b) explicitly opt into the longer-TTL cache write if the enrichment queue is expected to drain more slowly than that.

### 5.2 Priority, not just budget: what production indexers actually prioritize

A budget cap alone doesn't decide *what* gets the budget first. Two real systems give AWB a concrete prioritization scheme to copy. TypeScript's `tsserver` background-compiles "projects with open files" ahead of the rest of the workspace specifically for IDE responsiveness (§1.2) — the direct analogue is prioritizing LLM re-promotion for whatever folder is currently open in AWB's Ontology Graph UI. Sourcegraph's code-intel auto-indexing service runs its scheduling sweep on a fixed interval (documented default: every 2 minutes) but explicitly rate-limits and batches the *work* it considers: a configurable batch size (documented default: 2,500 repositories per cycle) and a maximum-repositories-inspected-per-second cap, plus a minimum 24-hour cooldown before the same repository is reconsidered for a full re-index (https://sourcegraph.com/docs/code-search/code-navigation/auto_indexing). Translated to AWB's Tier-3 scheduler, this argues for three independent knobs, not one: (a) a **sweep interval** (how often the re-promotion queue is even inspected), (b) a **per-sweep batch cap** (how many stale nodes get promoted per sweep, so a single mass-invalidation — e.g., a formatting-only commit that touches every file's `content_hash` without changing any `signature_hash`, per §4.2 this shouldn't even reach here, but defense in depth matters — can't blow the whole budget in one pass), and (c) a **per-node cooldown** (don't re-summarize the same hot node twice within N minutes even if it keeps flipping stale, coalescing bursts). This composes with, and does not replace, the priority ordering already specified in `research-ontology.md` §4.2/§9 (open folder > active-ticket folder > top-N centrality).

### 5.3 Debounce: coalescing bursts before they ever reach the queue

Industry practice for live/background reindexing is a short **quiet-window debounce** at the file-watcher layer — wait for a burst of saves to go quiet for some small interval (commonly a few hundred milliseconds to a couple of seconds in editor/LSP tooling) before triggering a reindex pass, so that ten keystrokes in ten seconds coalesce into one Phase-A run instead of ten. This is standard enough to be closer to folklore than a single citable paper, but it composes cleanly with everything above: debounce bounds *how often* Phase A/B run at all; content-hash comparison (§1, §4.2) bounds *what* they do once they run; the priority queue and cooldown (§5.2) bound *how much* Tier-3 work a burst of Phase-B invalidations can enqueue. AWB's own measured numbers make the debounce window an easy choice: at 82k lines/s for Tier 1 and the CodeQL-measured "up to 15 seconds for a fully-incremental update on a commit touching 1000 lines" as an upper bound for a much heavier Datalog pipeline (https://arxiv.org/abs/2308.09660), a single-file Phase A/B pass on AWB's lighter tree-sitter-plus-heuristic-resolver stack should be comfortably sub-second, meaning a 1–2 second debounce window is generous headroom, not a bottleneck.

### 5.4 Bounding fan-out: why "one symbol changed" can mean thousands of dependents, and why it's usually fine

The research brief's framing — a widely-referenced symbol changing has a large fan-out — is empirically real, not a hypothetical worst case. A peer-reviewed study of dependency graphs across 12 Java applications and 14 type-relationship kinds found that **in-degree (how many other locations reference a given type) follows a power-law distribution while out-degree follows an exponential one** — a small number of types are referenced by a disproportionate share of the rest of the codebase, which the authors attribute to a "rich-get-richer" effect compounded by an awareness gap: a programmer controls what their own code depends on (bounding out-degree) but has no equivalent visibility into how many other places come to depend on their code over time (https://arxiv.org/abs/0802.2306). Combined with AWB's own measured reference density (243.6 references/kLOC, `research-extraction.md` §1), this means a handful of foundational symbols in any AWB workspace will legitimately have reverse-index fan-in in the thousands once the repo reaches the multi-MLOC range the feature targets.

The resolution is that §4.2's signature/body split and §4.4's demand-driven deferral already do almost all of the necessary work: (a) most edits to a hot symbol are body-only and never reach Phase B at all; (b) even a genuine signature change to a hot symbol only re-runs the *cheap* Tier-1.5 heuristic resolver against its (large) reverse-index set, not the *expensive* Tier-3 LLM pass — Phase B marks affected `semantic` edges `stale`, it does not re-summarize them; (c) re-promotion of those staled edges is explicitly demand-driven and budgeted (§4.4, §5.2), so a single hot-symbol edit enqueues thousands of stale flags but the LLM budget only ever pays for the ones a user or ticket actually surfaces. The one place fan-out genuinely does cost real, unavoidable work is the **containment-ancestor** re-summarization HCGS-style bottom-up enrichment requires (`research-extraction.md` §2.13, `research-ontology.md` §4.2) — but that fan-out is bounded by tree *depth* (function → class → file → folder → repo, a handful of hops), not by reference fan-in, and is exactly the case prompt caching over the shared ancestor-chain prefix (§5.1) amortizes well.

## 6. Recommended architecture for AWB's dev-loop

Putting §1–5 together into the concrete, implementable shape:

**On every file save (debounced, §5.3):**
1. Compute `file_content_hash` (already decided). If unchanged, stop — no work at all (this alone eliminates saves that don't touch content, e.g. an editor re-save).
2. Re-run Tier 1 (tree-sitter) on the changed file only — a topological, single-file scheduler (§4.1), sub-100ms per file at AWB's measured throughput.
3. Diff the new symbol table against the old one **by `symbol_id`**, not by position (§1.3's load-bearing lesson). For each symbol: unseen → insert; seen with unchanged `content_hash` → no-op; seen with changed `content_hash` → recompute `signature_hash` and compare (§4.2); missing → soft-delete (`valid_to_commit`, already decided in `research-ontology.md` §8.6/§7).
4. For symbols whose `signature_hash` changed, was newly added, or was removed: query `reverse_edge_index(dst_symbol_id)` (§3, §4.2 Phase B) — file-level index first, symbol-level index second, mirroring Nx's coarse-then-fine design (§2.3) — skipping any partition tagged `stable`/`frozen` unless that partition's own revision moved (§4.3). Re-run Tier-1.5's confidence-scored resolver only for the returned files' outgoing edges.
5. For every `semantic`/`derived` edge whose cited `evidence_ref[].content_hash` no longer matches: flip to `stale` (already decided, §4.2 Phase C). Do **not** re-summarize synchronously.

**On a background sweep (interval-based, §5.2, decoupled from the save path entirely):**
6. Drain the `stale` queue in priority order — open folder, then active-ticket folder, then centrality (already decided in `research-ontology.md`) — subject to a per-sweep batch cap and a per-node cooldown.
7. Group the drained batch by shared ancestor-chain prefix (same file/class/folder) and submit via the Anthropic Batch API (§5.1) when the queue is large/latency-insensitive, or synchronous+prompt-cached calls when a user is actively waiting on a specific folder's promotion (UI-triggered "enrich this now").

**On `git diff`-scoped commit-level reindex (not per-save, e.g. on branch switch or a large external edit), reuse the identical Phase A/B/C algorithm above, scoped to `git diff <last_indexed_commit>..HEAD --name-status -M` instead of a single file** — rename detection (`-M`) matters concretely here: a `R100 old_path new_path` line should update the existing `File` node's path in place (preserving its `symbol_id`s and history) rather than soft-deleting and re-inserting, avoiding the exact kind of spurious churn CodeQL's id-stability fix was built to eliminate (§1.3).

**Schema additions this implies on top of `research-ontology.md`'s §8.5 property sets** (all additive, none of it contradicts the existing design): a `signature_hash` column on `Callable`/`Type`/`Field` nodes, distinct from `content_hash`; a `durability ∈ {volatile, stable, frozen}` column on `File`/`Repository`/`ExternalPackage`; a materialized `reverse_edge_index(dst_symbol_id, src_file_id)` table (derivable from the existing edge table's `(graph_id, dst_id, type)` index, but worth a dedicated narrow table for the hot Phase-B lookup path); and a small `enrichment_queue(node_id, priority, staled_at, cooldown_until)` table backing §5's scheduler.

## 7. Top traps

**1. Don't attempt "fully incremental" everywhere — it costs memory, not time, and the memory cost is brutal.** CodeQL's own prototype incremental solver, made *fully* incremental end-to-end (no from-scratch fallback anywhere in the pipeline), needed **more than an hour to initialize and up to ~70 GB of memory**, versus a *hybrid* design (non-recursive parts recomputed from scratch on the bounded changed-input set, only the genuinely recursive Datalog fixpoint kept live-incremental) that initialized in ~15 minutes at ~20 GB and still delivered sub-minute, commit-size-proportional updates (https://arxiv.org/abs/2308.09660). AWB's own three-tier split (Tier 1 always cheap enough to redo from scratch on the changed-file set; Tier 1.5 incremental via the reverse index; Tier 2/3 explicitly batch/lazy, never live-incremental) is already the hybrid shape this evidence recommends — the trap is scope creep toward making Tier 2 or Tier 3 "live" to chase lower latency, which the CodeQL numbers say is the wrong trade.

**2. A deep constructive trace (single flat content hash) is the wrong cache shape for anything non-deterministic or anything needing fine-grained early cutoff.** Turborepo/Nx-style single-hash caching is excellent for Tier 1 file-level re-parse decisions (deterministic, no early-cutoff need finer than "the file"), but using the same pattern for Tier 3 LLM output would mean any upstream content change forces a full re-summarization with no ability to reuse a still-valid sibling summary — and worse, per Build Systems à la Carte's own caveat, a flat hash-of-everything cache is only *correct* when the underlying computation is deterministic, which an LLM call is not (§2.1, §4.1).

**3. Don't let the reverse-index walk become the thing that's O(repo) instead of the change.** The naive version of §3/§4.2 — "a symbol changed, so mark every file that could possibly reference it as needing full re-extraction" — reproduces exactly the CodeQL failure mode (§1.3, §7.1) at the AWB-schema level: without the signature/body split (§4.2) and the durability pre-filter (§4.3), *any* edit to a hot, `frozen`-tier utility function would walk a multi-thousand-row reverse-index result set (§5.4) on every keystroke. The fix is not a bigger cache, it's the two filters that stop the walk from starting in the first place.

**4. Rename-blindness manufactures the same churn unstable ids do.** A `git diff` step that treats a rename as delete+insert (instead of using `-M` and updating the existing node's path) forces every downstream reverse-edge lookup, soft-delete/insert bookkeeping, and `stale` flag to fire for a file that, semantically, didn't change at all — the CodeQL lesson (§1.3) recurring at the git-integration layer instead of the id-assignment layer.

**5. Prompt-cache TTL is an operational constraint on batch-window sizing, not a detail to discover in production.** With a default cache TTL reported around 5 minutes (as of an early-2026 Anthropic pricing change) versus a 25%-premium 1-hour option, an enrichment scheduler that drains its priority queue in bursts spaced further apart than the TTL will silently pay full input price on every batch instead of the intended 90% cache-read discount (§5.1) — the sweep interval and per-sweep batch cap (§5.2) should be tuned together with which cache-TTL tier is requested, not independently.
