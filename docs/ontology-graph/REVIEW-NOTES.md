# Ontology Graph DESIGN.md — Adversarial Review Audit Trail

Date: 2026-08-22. This is the audit trail for how `DESIGN.md` (v1.1) responded to a three-lens adversarial review of v1.0. It has two parts per lens: (1) the reviewer's findings, reproduced **verbatim**, and (2) a 1:1 resolution for each individual finding — `ADOPTED` (the design changed to fully satisfy the finding), `MITIGATED` (a concrete change was made, but full resolution requires empirical work a design document cannot itself perform, e.g. a real benchmark), or `REJECTED` (the finding, or a specific sub-claim/sub-option within it, is not incorporated, with a stated reason). Every finding is mapped; none is silently dropped.

**Scorecard**: 21 findings total (7 scale, 7 integrity, 7 adoption). 18 `ADOPTED`, 3 `MITIGATED` (S1, S3, S4 — all three because the reviewer's own suggested fix included a "measure/benchmark this" clause that only a real, running system can satisfy, not a design document). Three findings additionally contain an explicit sub-option `REJECTED` inside an otherwise-adopted resolution (S1's "move the flush off the main thread," S6's implicit "FTS5 is free" premise, A1's "auto-trigger on Resource registration") — called out individually below, not hidden inside a blanket "adopted."

Each finding's resolution names the exact place in `DESIGN.md` where the fix lives, tagged inline there with `(review finding, <lens>/<severity>)` so the two documents can be cross-referenced in either direction.

## Scale lens (7 findings)

### S1 [critical] — sql.js flush blocks the whole instance as ontology tables grow

> Axis 3: "SQLite (sql.js, dev) / PostgreSQL (prod) is the only storage engine" — research-storage.md's own charter is to validate this "actually holds up at AWB's projected scale... on both required backends."
> Problem: sql.js flush (apps/server/src/db.ts:557-566, called from a 30s-default timer at :578-588) is a full synchronous database re-export: `dataSource.sqljsManager.saveDatabase()` -> TypeORM's sqljs driver calls `db.export()` then `fs.writeFileSync(location, out)` (confirmed at db.ts:762-763) on the WASM main thread. The dirty flag that triggers this (db.ts:61-105) is set by ANY non-SELECT write anywhere in the app, and there is exactly one shared `database/data.db` file for the whole AWB instance (db.ts `resolveSqljsLocation()` — no per-workspace split). This exact mechanism already caused a real production incident that AWB fixed once (ticket d5a8594a, cited verbatim in db.ts:40-56): under high write FREQUENCY it re-serialized the whole DB on every write, so the fix was to batch to a 30s cadence. That fix reduces frequency, not per-flush COST, which is O(total DB size). At the design's own 10 MLOC extrapolation (280k def nodes + up to 2.4M raw ref edges, aggregated 3-10x per DESIGN.md's own "aggregate, never raw" invariant to ~240k-800k edge rows), a single large workspace's OntologyNode/OntologyEdge tables can add tens to hundreds of MB to that one shared file. Every subsequent flush — triggered by an unrelated ticket comment or SSE log line anywhere in AWB — now re-serializes and re-writes that enlarged file synchronously, blocking the ENTIRE instance's request handling for every user, not just ontology-graph users, on a recurring 30s cadence for the life of the process. Neither DESIGN.md nor research-storage.md nor research-incremental.md discuss this; research-storage.md's only "flush" mention (§1, §4.1) is about DuckDB read-staleness, never write-side blocking cost — despite its own opening promise to validate both backends at scale.
> Suggested fix: Either isolate ontology tables into a separately-flushed sql.js file so their growth doesn't inflate the OLTP file's export cost, or explicitly document/enforce a row-count ceiling above which the ontology feature degrades or is disabled on the sql.js backend, or move the flush off the main thread and make it size-aware/incremental rather than a fixed-cadence full re-export — and measure actual `db.export()` wall time at the design's own projected row counts before shipping.

**Resolution: MITIGATED.** Adopted the reviewer's first two suggested branches together (belt-and-suspenders, not either/or): axis 3's Decision now specifies a **second, independently-flushed sql.js `DataSource`/file dedicated to ontology tables** (own dirty flag, own flush timer, own `serializeSqljsTransactions()` queue — never sharing any of the three with the primary `data.db`), sql.js/dev-only, Postgres unaffected (single DataSource, as before) — plus a **row-count ceiling** (`ONTOLOGY_SQLJS_ROW_CEILING`) as defense-in-depth for the residual risk that one workspace's ontology growth still slows other workspaces' ontology-only flushes. The third branch — moving the flush off the main thread — is explicitly **REJECTED** as a v1 mechanism: `sql.js`'s WASM-resident `Database` object cannot safely cross a `worker_threads` boundary without a flush-ownership redesign this document does not size; it is named as a real, documented follow-up (`DESIGN.md` §10a item 12), not adopted now. The reviewer's closing clause — "measure actual `db.export()` wall time... before shipping" — is written into the design as a **mandatory pre-ship gate on child ticket #1**, not performed here; a design document cannot itself run that benchmark, which is why this finding is `MITIGATED` rather than fully `ADOPTED`. See `DESIGN.md` axis 3 Decision (the "Ontology tables get their own, independently-flushed sql.js DataSource/file in dev" paragraph) and axis 3 Rejected ("Moving the sql.js flush off the main thread as a v1 mechanism").

### S2 [critical] — sigma.js default-renderer safety net rests on an unverified, explicitly-hedged assumption

> Axis 5's default-renderer safety net: "the aggregated/community view of even a 10 MLOC repo collapses ~280k definition nodes into what is very likely hundreds to low thousands of Community/Module/File meta-nodes after Leiden clustering... it lands inside sigma.js's comfortable envelope, not past it" (research-visualization.md §2.5, adopted verbatim by DESIGN.md Axis 5).
> Problem: This unverified, explicitly-hedged ("very likely") assumption is the ONLY thing keeping the DEFAULT (non-opt-in) render path under sigma.js's own measured, primary-sourced ~5,000-node collapse point (research-visualization.md §2.3's four independent data points, e.g. issue #567: a 423-node/17k-edge graph already struggles). No document in the corpus ever reports an actual resulting community COUNT for any real code graph at this scale — Codebase-Memory's cited numbers (Django 49,398 nodes, Linux kernel 2.1M nodes) are for indexing speed/node-edge counts, never for how many Louvain/Leiden communities resulted. research-ontology.md's own schema supports a hierarchical fix (`Community(level, algorithm='leiden', parent_community_id, size, cohesion)`, line 214) — but research-visualization.md §4.8's actual rendering algorithm treats "Community" as one flat single-level tier with no logic to walk `parent_community_id` up to a level under the render budget, and no evidence the coarsest level would even be small AND meaningful rather than a handful of giant undifferentiated blobs. Leiden's own refinement phase (the connectivity-guarantee the design leans on throughout §5.1) tends toward fairly small, cohesive communities on real modular structure — if average community size at 280k nodes is in the tens rather than hundreds+, single-level community count lands at 5,000-15,000, already past sigma's ceiling on day one, with no real fallback: cosmos.gl's opt-in mode is explicitly scoped for "more detail" (raw/expanded), not "even the aggregated view is too big," and its own layout-stability primitive is documented as strictly weaker (research-visualization.md §3.3).
> Suggested fix: Measure actual Leiden community count/size distribution on a real large multi-MLOC repo before committing sigma.js as the unconditional default, or make the render tier explicitly budget-aware — walk `level`/`parent_community_id` to the coarsest level under ~2,000 nodes, with a defined fallback (paginated community list, or a second coarsening pass) if even the top level exceeds sigma's ceiling.

**Resolution: ADOPTED.** The reviewer offered an either/or; the design now does both. Axis 5's Decision no longer commits sigma.js as *unconditional* default — a pre-ship measurement of real Leiden community count/size distribution on a multi-MLOC repo is now a stated precondition — **and**, independent of that measurement's outcome, the render tier is made explicitly budget-aware: `graphology-communities-leiden`'s hierarchical output (`level`/`parent_community_id`, already schema'd in `research-ontology.md`) is walked from the finest level upward until the node count drops under a ~2,000-node render budget, with a defined fallback (paginated community list / second coarsening pass) if even the coarsest level still exceeds sigma's ceiling. This directly fixes `research-visualization.md` §4.8's flat single-level treatment the finding identified. See `DESIGN.md` axis 5 Decision ("The sigma.js-as-unconditional-default is now gated on a pre-ship measurement...") and axis 5 Rejected ("A single fixed community-detection level as the render tier").

### S3 [major] — the global sqljs transaction-serialization queue means ontology bulk writes block the rest of AWB, and vice versa

> Axis 4's incremental pipeline "keeps a single-file edit sub-second" and, more broadly, treats extraction/incremental-refresh writes as not contending with the rest of the running app.
> Problem: `serializeSqljsTransactions()` (db.ts:159-186) FIFO-queues every `dataSource.manager.transaction()` call across the WHOLE sqljs DataSource, not scoped to ontology tables, because sql.js has exactly one WASM connection/query-runner (the fix's own comment at db.ts:108-124 explains the shared-runner race it closes). Any transactional write the extraction worker or Phase A/B incremental-refresh issues to populate/update OntologyNode/OntologyEdge — a natural TypeORM batch-insert pattern — queues behind, and blocks, every concurrent transactional write elsewhere in AWB (ticket moves, comments, agent-dispatch bookkeeping), and vice versa, for its full duration. DESIGN.md never specifies a transaction-batching strategy for the initial bulk-population write (280k+ node rows, hundreds of thousands of edge rows even after aggregation) or for Phase B's fan-out burst, which research-incremental.md §5.4 itself says can hit reverse-index fan-in "in the thousands" for a hot symbol at target scale. If that burst issues one `transaction()` per file or per batch, each takes its full turn in the single global FIFO queue while the rest of the app's writes wait.
> Suggested fix: Specify that ontology bulk writes minimize the NUMBER of `transaction()` calls (large batched inserts, or raw `dataSource.query()` outside the transaction manager) rather than just total row count, and document/measure the expected wall-clock duration a full-repo initial population run would hold the rest of AWB's dev writes queued behind it.

**Resolution: MITIGATED.** The cross-contamination this finding describes (ontology writes blocking ticket/chat/dispatch writes, and vice versa) is fully closed as a **direct side effect of S1's dual-DataSource fix**: `serializeSqljsTransactions()` is applied per-DataSource, so the new ontology DataSource gets its own independent FIFO queue that no longer contends with the primary DataSource's queue — a resolution stronger than what the finding's own suggested fix asked for, called out explicitly in `DESIGN.md` as "a direct, positive side effect." The reviewer's specific suggested fix — minimize the *number* of `transaction()` calls via batching — is adopted verbatim as a requirement on the (now-isolated) ontology DataSource's own queue, since one-transaction-per-file would still serialize ontology-internal writes behind each other unnecessarily. `MITIGATED` rather than `ADOPTED` because the "document/measure the expected wall-clock duration" clause is, like S1, written into the design as a required child-ticket benchmark rather than performed here. See `DESIGN.md` axis 3 Decision ("`serializeSqljsTransactions()`'s FIFO queue is per-DataSource...").

### S4 [major] — Tier-3 cost figures were never recomputed for the actually-adopted (aggregate-only) approach

> Axis 1's Tier-3 mitigation — "applied only to aggregate nodes (folder/module/class — never function)... never a default-on per-symbol pass" — presented as the fix for "the single biggest cost-blowup risk in the feature" (research-extraction.md §2.13/§6 trap #5).
> Problem: Every cost figure anywhere in the corpus ($10-30/MLOC, ~28k calls/MLOC) is computed for the explicitly-REJECTED per-function approach; it is never recomputed for the ADOPTED aggregate-node-only approach. Using the design's own aggregate-node estimate (research-storage.md §6.3: ~100k-150k aggregate nodes — class+interface+file+folder — at the 10 MLOC/280k-def scale), restricting to aggregate nodes only cuts call COUNT by ~2x relative to the rejected per-function estimate (280k vs ~100-150k), not the order of magnitude the "biggest cost-blowup risk, fixed" framing implies. Per-call token cost for bottom-up HCGS-style aggregate summarization (full file/folder content plus already-computed child summaries, per research-extraction.md §2.13's own cited technique) is inherently LARGER than the ~600-token/call baseline the rejected estimate used, not smaller. A first full-population pass over a newly onboarded large repo has no warm prompt cache (research-incremental.md §5.1's own ~5-minute default TTL caveat means a slowly-draining initial sweep may never realize the claimed 90% cache-read discount), so the realistic first-pass cost is plausibly in the same order of magnitude the rejected approach was disqualified for — this is never computed, checked, or ruled out anywhere.
> Suggested fix: Compute and publish an actual cost/latency estimate for a full first-pass Tier-3 enrichment at the ~100-150k-aggregate-node scale (realistic per-call token count, with and without batch/caching discounts) the same way research-extraction.md did for the rejected approach, and size the opt-in budget default around that real number rather than the rejected approach's number.

**Resolution: MITIGATED.** Performed the honest recomputation the finding asks for, using only numbers already published in this corpus: ~100k–150k aggregate nodes (`research-storage.md` §6.3) × a reasoned ~1,500–4,000 input-tokens/call range for file-plus-child-summary HCGS calls (explicitly flagged in the design as "a reasoned estimate... not a benchmark") ≈ 150M–600M input tokens, ≈ **$75–$300** at the already-cited $0.50/M rate — landing in the *same order of magnitude* as the rejected per-function estimate's own $100–300 ballpark, exactly confirming the finding's core claim that the "biggest cost-blowup risk, fixed" framing overclaimed. `MITIGATED` rather than `ADOPTED`: this recomputation is honest arithmetic on existing figures, not the real empirical benchmark the suggested fix ultimately calls for ("the same way research-extraction.md did," i.e. an actual measurement) — that is written into child ticket #9 as a required pre-ship step, sized against this recomputed range rather than the rejected approach's number. See `DESIGN.md` axis 1 Decision ("Tier-3 first-pass cost, recomputed...") and §11 ticket #9.

### S5 [major] — the background sweep's throttle knobs cap cost, not staleness arrival rate; convergence was never modeled

> DESIGN.md Axis 4: "A background sweep later drains the stale queue in priority order... under a token budget" — implying the semantic/derived layer converges to fresh over time.
> Problem: The sweep's three throttling knobs (sweep interval, per-sweep batch cap, per-node cooldown; research-incremental.md §5.2) are deliberately sized to cap COST, not to track staleness ARRIVAL rate. research-incremental.md §5.4 itself establishes that in-degree in real code graphs follows a power law and that fan-in "in the thousands" for foundational symbols is realistic at the multi-MLOC scale the feature targets — so continuous multi-contributor edit activity on a large active repo will continuously flip (Phase C) a nontrivial fraction of the semantic layer's evidence hashes to stale. No document anywhere models the steady-state relationship between arrival rate (edit velocity x fan-out-to-ancestor-chain) and the capped drain rate. If arrival structurally exceeds the deliberately-throttled drain rate on a sufficiently large, sufficiently active repo, the stale backlog grows monotonically instead of converging, contradicting the "sweep... drains the queue" framing — and this is exactly the regime (5-6+ MLOC, active team) the task is asking this design to hold at.
> Suggested fix: Model expected staleness arrival rate at target scale against the chosen sweep knobs' maximum drain rate; either size the budget to keep drain >= arrival at the stated scale target, or explicitly document that large active repos will run a perpetually-growing semantic-layer backlog and surface that honestly via the `indexed_at`/`confidence` freshness fields rather than implying eventual convergence.

**Resolution: ADOPTED.** Chose the reviewer's own second explicitly-offered branch in full: the design no longer implies convergence. Axis 4's Decision now states plainly that the sweep's three knobs are "a cost cap, not a staleness-convergence guarantee," names §5.4's power-law fan-in finding as the reason a sufficiently large/active repo can see the backlog grow rather than shrink, and commits to honest surfacing at both consumption points — every MCP response's `{indexed_at, confidence}` (already mandated) and the new UI freshness badge (axis 5, see A2) — rather than an unverified convergence claim. A telemetry Done-when (ticket #6, shared with A5's mechanism) logs real stale-queue size/age data so a *future* revision could attempt the "model arrival vs. drain" branch the reviewer also offered, once real data exists to model against — that branch was not chosen now because no document in this corpus, including this revision, has the underlying arrival-rate data to model honestly today. See `DESIGN.md` axis 4 Decision ("The background sweep is a cost cap, not a staleness-convergence guarantee...") and axis 4 Rejected ("Claiming sweep convergence at a specific scale target without arrival-rate data").

### S6 [minor] — the fuzzy-match tier has no stated data structure or complexity bound

> DESIGN.md/research-extraction.md's characterization of Tier 1.5 as "a separate, cheap, whole-workspace pass" using a confidence cascade that bottoms out in a "fuzzy" (~0.35 confidence) match tier.
> Problem: No document states a data structure or complexity bound for the fuzzy tier. If implemented as pairwise string-similarity between an unresolved reference and workspace symbol names — a natural first implementation of "fuzzy match" — it is the one place in an otherwise carefully bounded design (extraction is linear per research-extraction.md §1; storage/query is rigorously depth-capped per research-storage.md §2.4) that could become genuinely O(refs x defs). At the design's own measured density (243.6 refs/kLOC, 27.6 defs/kLOC), even a modest 5% fuzzy-fallback rate at 10 MLOC is ~120k references potentially compared against a ~280k-symbol table each — not "cheap" by any standard this design applies elsewhere.
> Suggested fix: Specify the fuzzy tier's implementation (e.g. an indexed structure — trigram index, BK-tree, or SQLite FTS5, which is compiled into sql.js and so avoids the WASM-loadable-extension wall research-storage.md §6.1 already flags for other extensions) and state its complexity bound explicitly, matching the rigor applied to every other tier in this design.

**Resolution: ADOPTED, with a factual correction.** The core ask — specify a data structure and complexity bound for the fuzzy tier — is fully adopted: axis 1's Decision now specifies an in-process JS-side BK-tree over the workspace symbol-name table, giving O(log n) lookups (≈ a few million comparisons for a 5%-fallback/10 MLOC workload) instead of the O(refs × defs) risk the finding correctly identifies. **The finding's own parenthetical, "SQLite FTS5... is compiled into sql.js," is factually incorrect and is corrected, not adopted**: verified against `sql.js`'s own build documentation/Makefile, the project's default distributed build enables FTS3 only — FTS5 requires a custom Emscripten rebuild with `-DSQLITE_ENABLE_FTS5`, the same "fork `sql.js`" cost class `research-storage.md` §6.1 already rejected for `sqlite-vec`. Using FTS5 as proposed would have reintroduced exactly the dependency-fork cost this design rejects elsewhere for consistency; the BK-tree was chosen instead specifically because it needs no SQLite extension of any kind, loadable or compiled-in, closing the finding's real concern without the factual error. See `DESIGN.md` axis 1 Decision ("Fuzzy tier is a bounded-complexity, dependency-free structure...") and axis 1/axis 3 Rejected ("SQLite FTS5 for the fuzzy tier").

### S7 [minor] — the "sub-second" headline claim silently drops the one case its own source flags as expected at scale

> DESIGN.md's bottom-line-up-front (line 9): the incremental pipeline "keeps a single-file edit sub-second."
> Problem: research-incremental.md §5.3's "sub-second" language is scoped to a generic single-file Phase A/B pass and does not cover the case its own §5.4 flags as realistic at scale: "a genuine signature change to a hot symbol" whose reverse-index fan-in "will legitimately have... fan-in in the thousands" once the repo reaches the multi-MLOC range the feature targets. Phase B for that case re-runs the Tier-1.5 resolver against every one of those files' outgoing edges. No document anywhere estimates that case's actual latency, so DESIGN.md's unqualified headline claim silently drops the one scoped exception its own source research explicitly calls out as expected at target scale.
> Suggested fix: Either measure/bound Phase B's latency for a hot-symbol signature change at realistic fan-in ("thousands"), or qualify the headline claim (e.g. "sub-second for the common case; hot-symbol signature changes are explicitly deferred/debounced") so the design doesn't overclaim a uniform SLA its own research contradicts.

**Resolution: ADOPTED.** Chose the reviewer's own second explicitly-offered branch: the bottom-line-up-front and axis 4's Decision both now qualify the claim exactly along the lines the finding suggests — "sub-second for the common case (body-only edits, and signature changes with typical, non-hot-symbol fan-in); hot-symbol signature changes at realistic multi-thousand fan-in are an explicitly separate, unmeasured case... not covered by the sub-second SLA, until a child ticket benchmarks it." This fully resolves the overclaim the finding identifies without requiring the (also-acceptable, but more expensive) measurement branch. See `DESIGN.md` preamble bottom-line-up-front and axis 4 Decision ("The 'sub-second' headline claim is now scoped to the case it actually covers...").

## Integrity lens (7 findings)

### I1 [critical] — no confidence floor on the three tools that actually walk edges; no path-level confidence rollup

> Axis 6's MCP contract ('every symbol/match carries {source, confidence, indexed_at, commit} plus an ordinal confidence_bucket') is presented as the safeguard against misleading edges, and axis 6 claims to adopt research-agent-consumption.md's §5 'as the binding project decision.'
> Problem: The three tools that actually walk CALLS/REFERENCES edges — graph_neighbors, graph_blast_radius, graph_call_path (research-storage.md §2.4) — have no default confidence floor anywhere in the 8-document corpus, and DESIGN.md doesn't add one either. research-agent-consumption.md's concrete `confidence_min: z.number()...default(0.75)` Zod default (explicitly labelled 'research-extraction.md trap #4 default floor') is wired only into the two NEW resolution tools, graph_find_symbol and graph_search_symbols — never into the fixed three. research-storage.md's own illustrative SQL for the bounded-BFS 'reach' query (blast radius/neighbors) filters WHERE only on `r.depth < :max_depth`, `e.graph_id`, and a cycle guard; the graph_call_path BFS filters only on frontier/visited sets. Neither has a confidence predicate. Even DESIGN.md's own restatement of graph_find_symbol waters the source's concrete 0.75 number down to vague prose ('on a unique high-confidence match'). Net effect: by default, a fuzzy-matched CALLS edge at confidence=0.35 is traversed and returned by graph_blast_radius/graph_call_path with the same weight as a SCIP-verified confidence=1.0 edge, distinguished only by a field value the agent must notice and threshold itself — labeled, not filtered, in exactly the tools where a wrong edge does the most damage (e.g. 'what breaks if I change X'). Compounding this, no tool spec anywhere computes a path-level confidence rollup for graph_call_path, even though research-ontology.md §6.5 explicitly requires 'never multiply confidences along a path without recording that you did (path confidence is a derived, labelled quantity)' — a multi-hop path that only exists because of one 0.35-confidence hop is reported with no path-level honesty signal at all.
> Suggested fix: Pin an explicit default confidence_min (e.g. 0.75) into DESIGN.md's own axis 6 Decision text for graph_neighbors/graph_blast_radius/graph_call_path, add the predicate to the bounded-BFS SQL and BFS frontier query, and require graph_call_path to compute and return a labelled path-level confidence (e.g. min-along-path) rather than only per-edge confidence.

**Resolution: ADOPTED.** All three of the finding's concrete asks are implemented as stated: `confidence_min` (default `0.75`) is now a first-class parameter on **all six** graph-lookup/traversal tools, not just the two newest; the SQL predicate (`AND e.confidence >= :confidence_min`) is added to both the bounded recursive CTE (`graph_neighbors`/`graph_blast_radius`) and the BFS frontier query (`graph_call_path`) in axis 3; and `graph_call_path` now computes and returns a labelled `path_confidence` (min-along-path, explicitly never multiplied), closing the `research-ontology.md` §6.5 gap directly. See `DESIGN.md` axis 6 Decision ("A default confidence floor is now pinned into this Decision text for the three FIXED traversal tools too...") and the extended cross-cutting invariant in §3 ("Any multi-edge path this design returns carries exactly one labelled, derived path-level confidence...").

### I2 [critical] — rename/move handling never re-triggers Tier-1.5 resolution for the moved file's own outgoing edges

> Axis 4's incremental pipeline "Phase A/B/C algorithm and its rename handling ('rename detection updates the existing File node's path in place, preserving its symbol_ids') is presented as the complete fix for file rename/move.
> Problem: The fix as specified only prevents symbol_id churn — it never re-triggers Tier-1.5 cross-file resolution for the MOVED file's own outgoing edges. Phase A's early-cutoff gate is keyed on `signature_hash`, a pure function of the file's own declared symbol shapes; a pure rename/move changes neither `file_content_hash` nor any symbol's `signature_hash`, so per DESIGN.md's own text ('Phase A... stop here on no signature change') Phase B — the only phase that re-runs the Tier-1.5 resolver — never fires. This holds even on the git-diff-scoped batch path that explicitly detects the rename via `-M` (research-incremental.md §6: the R100 handling is described purely as 'update the existing File node's path in place... rather than soft-deleting and re-inserting,' with zero mention of re-resolving that file's own refs[]). But two of Tier-1.5's own cascade tiers are inherently path-relative — same-module (0.90) and import-suffix (0.85) — resolving based on the calling file's location relative to candidate targets. A file moved to a new directory with byte-identical content can have its relative-import resolution targets silently shift (e.g. a same-named sibling now closer) while every one of the design's own staleness signals (content_hash, signature_hash, evidence_ref hash) reports 'unchanged.' Nothing anywhere asks 'did this file's resolution CONTEXT change' — only 'did this file's own declared shape change' — so a stale/wrong edge from the moved file survives indefinitely; the background stale-queue sweep is itself evidence-hash-driven (content-based), so it wouldn't catch this either.
> Suggested fix: Add an explicit rename/move branch to Phase A that unconditionally re-runs the Tier-1.5 resolver for the moved file's own outgoing refs[], regardless of signature_hash — the cost is bounded (one file's ref list) and the correctness gap is otherwise silent and permanent.

**Resolution: ADOPTED, verbatim.** Phase A now has an explicit third, unconditional trigger alongside "signature changed": a detected rename/move (via `git diff -M`) always re-runs the Tier-1.5 resolver for the moved file's own outgoing `refs[]`, independent of `signature_hash`, closing exactly the path-relative-resolution-context gap the finding describes. The old "preserve `symbol_id`s on rename" behavior is kept (it was correct, just incomplete) and explicitly noted in the design as insufficient on its own. See `DESIGN.md` axis 4 Decision ("Rename/move is now an explicit, unconditional third Phase-B trigger...") and axis 4 Rejected ("Treating a rename as delete+insert... Extended in this revision").

### I3 [major] — nothing actually verifies that `confidence_method='agreement'` was computed the way the design's own cited evidence requires

> 'Agreement-derived, not LLM-self-reported' confidence is stated as a load-bearing principle backed by a `confidence_method ENUM('constant','agreement','support','calibrated','human')` column, framed alongside the layer write-scope rule under the same 'write-scope enforcement' banner in the bottom-line-up-front.
> Problem: The layer/type write-scope rule is a real, described mechanism: DESIGN.md §3 states it lives in the service layer ('an LLM/semantic extraction run may only insert Concept|Term|Policy|Actor|Capability nodes... it may never create, mutate, or delete a structural/derived row'). No equivalent mechanism is ever specified for the confidence VALUE's provenance. `confidence_method` is a plain enum column; nothing in axis 1 or axis 4's Tier-3 Decision text validates that a row with `confidence_method='agreement'` was actually computed via the k=3 self-consistency / independent-evidence-chunk-count algorithm research-ontology.md §6 point 3 proposes ('confidence = f(agreement across k independent samples/chunks)... never the model's stated probability'). That algorithm is cited only in the 'Why' section as supporting evidence for the axis-2 schema decision — it is never carried into axis 1/4's actual Decision text for how Tier-3 enrichment runs. A child ticket implementing Tier 3 (ticket #9) could satisfy every schema constraint DESIGN.md actually specifies while simply asking the LLM for a 0-1 confidence number in its structured-output prompt and writing it through with `confidence_method='agreement'` — exactly the practice the design's own cited evidence says produces meaningless numbers ('different LLMs... produce knowledge graphs that scarcely overlap... self-reported confidence is therefore not a measurement') — and nothing in the design would catch it, because the enum value is asserted, not verified.
> Suggested fix: Specify the confidence-computation mechanism as a concrete algorithm in axis 1/4's Decision text, not just cite it as background: the LLM extraction call must never be allowed to return a 'confidence' field at all (strip it from the response schema); a shared ingest helper computes confidence itself from k-sample agreement or evidence-chunk count and is the only code path permitted to set `confidence_method`. Treat this the same way the layer write-scope rule is treated — a validated invariant enforced in code, not a schema column an implementer can freely populate.

**Resolution: ADOPTED, verbatim.** Axis 1's Decision text now specifies exactly the mechanism requested: the LLM extraction call's structured-output response schema must never include a `confidence` field at all; a single shared ingest helper — living in the same service layer as the axis-2 layer write-scope check — computes `confidence` from k-sample agreement or evidence-chunk count and is the only code path permitted to write `confidence_method`. The cross-cutting invariants section (§3) was also extended so this reads as a validated invariant on par with the layer write-scope rule, not a second-class mention. ### I5 [major] — name-resolution confidence and runtime-dispatch confidence are collapsed into one number, including for SCIP edges

> research-ontology.md §6.2 treats tree-sitter-only edges as a solved problem via a flat 'confidence ≈ 0.75–0.9' discount for 'dynamic dispatch, duck typing, monkey patching, DI containers,' calling this 'the single most common trust bug in code graphs' as if it's fixed; SCIP edges are separately, unconditionally stamped 'confidence = 1.0, resolution = exact.'
> Problem: The Tier-1.5 cascade (import-map 0.95 → same-module 0.90 → import-suffix 0.85 → unique-name 0.75 → suffix 0.55 → fuzzy 0.35) grades confidence purely by which NAME-matching heuristic fired — it has no call-site-shape awareness. A call through an interface-typed or base-class-typed reference with N overriding implementations resolves to exactly ONE target via whichever name tier applies (often 'unique-name,' 0.75) and is stamped with that tier's confidence, which measures 'how sure am I this identifier names symbol X,' not 'how sure am I X is what executes at runtime' — a distinct, unaddressed axis of uncertainty for a polymorphic call site. The design's own OVERRIDES structural edge could be joined against a CALLS edge's target to detect and flag this, but no join, downgrade, or warning is specified anywhere. It gets worse, not better, at Tier 2: SCIP resolves to the compiler-declared symbol (e.g. the interface method) — a genuinely exact NAME reference — yet DESIGN.md blanket-stamps any SCIP edge confidence=1.0, collapsing 'exact reference to a declaration' and 'exact claim about what executes at runtime' into one number for exactly the call sites (polymorphic dispatch) no compiler-grade indexer can close without whole-program points-to analysis, which the design explicitly puts out of scope (Joern/CPG rejected in axis 1). Axis 2's own Decision text also never pins the `resolution` enum's actual values ('exact, name_match, dynamic, unresolved' per research-ontology.md §6.2) — it only names the column — so even the one field that could flag 'this edge might be dynamic dispatch' isn't a committed part of the binding decision.
> Suggested fix: Separate the two confidence dimensions explicitly: keep the existing cascade for name-resolution confidence, and add an independent discount (or explicit enum flag alongside confidence_bucket) computed by checking whether the resolved target has OVERRIDES/IMPLEMENTS siblings — if so, cap resolution at 'dynamic' regardless of which name tier matched. Pin the resolution enum's values in axis 2's Decision text, not just cite them in Why.

**Resolution: ADOPTED, verbatim.** Axis 2's Decision text now (a) pins `resolution ENUM('exact', 'name_match', 'dynamic', 'unresolved')` directly, not just cited from Why, and (b) specifies the exact mechanism suggested: a mandatory post-processing join checks whether a resolved `CALLS` target has any `OVERRIDES`/`IMPLEMENTS` incoming edges; if so, `resolution` is capped at `'dynamic'` regardless of which tier or indexer (including SCIP) produced the name match, while `confidence` itself remains the name-resolution cascade's own number — the two axes are explicitly kept separate rather than blended. See `DESIGN.md` axis 2 Decision ("`resolution` is now a pinned enum..." and "Name-resolution confidence and runtime-dispatch confidence are two different axes...") and the extended §3 invariant on `resolution`.

### I6 [major] — reflection/decorator-driven dispatch (including AWB's own NestJS DI) is an unaddressed, undifferentiated blind spot

> The design's false-positive treatment (research-ontology.md §6, research-extraction.md trap #4) is framed as covering the known failure modes of heuristic resolution, and axis 6 dogfoods the feature's own MCP tools directly against AWB's own NestJS server codebase (citing get_board_summary, TOOL_AUTHZ_TABLE, ticket-ref-capture.ts as the worked precedent).

### I7 [minor] — barrel/re-export chains may not resolve at import-map (0.95) confidence, understating confidence on AWB's own reference codebase

> research-extraction.md trap #4 lists 're-exports/barrel files' among the cases the generic confidence-discount cascade already handles, implying it's an adequate mitigation.
> Problem: A barrel re-export chain (`export { Foo } from './foo'`, re-exported through further index.ts levels) is not actually ambiguous or dynamic — it is 100% statically resolvable, just requires following N hops of indirection instead of one direct import. The design never specifies whether Tier-1.5's import-map tier (0.95, the one tier that could deterministically resolve this with no loss of precision) actually follows multi-hop `export...from` chains, or whether it stops at the first hop and falls through to unique-name/suffix (0.55-0.75) purely because the literal import specifier doesn't directly name the defining file. AWB's own codebase is cited repeatedly throughout DESIGN.md's own integration points as using exactly this pattern (`apps/server/src/entities/index.ts` barrel-exporting every entity) — so on the design's own primary worked example, an entity import resolved through that barrel would, as specified, likely register at 'likely' (0.55-0.75) confidence at best rather than 'asserted' (0.95+), understating confidence in the single most common case in the design's own reference codebase, and risking an outright wrong pick if two barrels in a larger monorepo re-export same-named symbols.
> Suggested fix: Specify that the import-map tier resolves transitively through re-export/barrel chains (follow export...from statements to their ultimate defining file before falling back to lower tiers), and add a repo-representative test fixture (a barrel file mirroring entities/index.ts) to the extraction-worker (#2) and resolver (#3) child tickets' test suites.

**Resolution: ADOPTED, verbatim.** Axis 1's Decision now specifies that the import-map tier (0.95) follows `export ... from` re-export chains to their ultimate defining file before falling through to lower tiers, bounded by the calling file's own import-graph depth. A repo-representative test fixture mirroring `apps/server/src/entities/index.ts` is added to child ticket #3's scope (resolver), as suggested. See `DESIGN.md` axis 1 Decision ("Import-map tier resolves transitively through barrels/re-exports...") and §11 ticket #3.
